================================================================================
           CQRS — COMMAND QUERY RESPONSIBILITY SEGREGATION
================================================================================

================================================================================
1. WHAT IS CQRS?
================================================================================
CQRS stands for Command Query Responsibility Segregation. It is an architectural pattern that separates the responsibility of handling READ operations (Queries) from WRITE operations (Commands) into two distinct models.

In a traditional CRUD system, the same model and the same database table are used for both reading and writing data. CQRS challenges this by saying:
"The model you use to UPDATE information should be different from the model you use to READ information."

CORE IDEA IN ONE LINE:
----------------------
  Commands → change state (write)
  Queries  → return state (read)
  These two responsibilities should NEVER be mixed.

COINED BY:
----------
Greg Young introduced the term "CQRS" around 2010, building on the earlier
"Command Query Separation (CQS)" principle by Bertrand Meyer (1988).

================================================================================
2. ORIGIN & HISTORY
================================================================================

CQS — The Parent Principle (Bertrand Meyer, 1988):
---------------------------------------------------
Bertrand Meyer, in his book "Object-Oriented Software Construction," defined
the Command Query Separation (CQS) principle at the METHOD level:

  - A method is either a COMMAND (modifies state, returns nothing)
  - Or a QUERY (returns data, modifies nothing)
  - A single method should NEVER do both.

Example of CQS violation:
  int pop() {  // BAD — modifies the stack AND returns a value
      int top = stack.peek();
      stack.remove(top);
      return top;
  }

CQS-compliant version:
  int peek()   { return stack.top(); }   // Query — only reads
  void pop()   { stack.remove(); }       // Command — only writes

CQRS — Elevating CQS to Architecture Level (Greg Young, ~2010):
----------------------------------------------------------------
Greg Young took the CQS idea from method-level to the architecture level,
applying it to entire systems, not just individual methods. Instead of
separating read/write at the method level, CQRS separates them at the
model, database, and service level.

================================================================================
3. CORE CONCEPTS — COMMAND vs QUERY
================================================================================

COMMANDS:
---------
- Represent an INTENT TO CHANGE state
- Express what the user or system wants to DO
- Named in imperative form (verb + noun)
- Do NOT return data (or return only an ID/acknowledgment)
- Can be REJECTED (validation can fail)
- Are handled by Command Handlers

Examples of Commands:
  PlaceOrderCommand      { userId, productId, quantity }
  CancelOrderCommand     { orderId, reason }
  RegisterUserCommand    { name, email, password }
  UpdateShippingAddress  { orderId, newAddress }
  ProcessPaymentCommand  { orderId, cardDetails }

QUERIES:
--------
- Represent an INTENT TO READ data
- Express what the user or system wants to SEE
- Named in question form (Get, Find, List, Fetch)
- Always return data
- NEVER modify state
- Are handled by Query Handlers

Examples of Queries:
  GetOrderByIdQuery      { orderId }         → returns OrderDetail
  ListOrdersByUserQuery  { userId, page }    → returns List<OrderSummary>
  GetProductCatalogQuery { category, filter} → returns List<Product>
  GetUserProfileQuery    { userId }          → returns UserProfile

KEY RULE:
---------
A Command should NEVER return business data.
A Query should NEVER change data.

This separation allows each side to be optimized, scaled, and evolved
independently.

4. CQRS ARCHITECTURE — DETAILED BREAKDOWN
================================================================================

HIGH-LEVEL DIAGRAM:
-------------------

                        ┌─────────────┐
                        │   CLIENT    │
                        │ (Web/Mobile)│
                        └──────┬──────┘
                               │
               ┌───────────────┴───────────────┐
               │                               │
        WRITE side                         READ side
               │                               │
    ┌──────────▼──────────┐        ┌───────────▼───────────┐
    │   Command Handler   │        │    Query Handler       │
    │  (validates intent) │        │  (fetches view data)   │
    └──────────┬──────────┘        └───────────┬───────────┘
               │                               │
    ┌──────────▼──────────┐        ┌───────────▼───────────┐
    │   Domain Model      │        │    Read Model          │
    │   (Aggregates)      │        │ (Projections/ViewDB)   │
    └──────────┬──────────┘        └───────────────────────┘
               │
    ┌──────────▼──────────┐
    │   Write Database    │
    │  (Normalized DB)    │
    └──────────┬──────────┘
               │
    ┌──────────▼──────────┐
    │   Event / Message   │  ← synchronizes write side to read side
    │   (Domain Events)   │
    └──────────┬──────────┘
               │
    ┌──────────▼──────────┐
    │ Projection Updater  │  ← rebuilds read model from events
    └──────────┬──────────┘
               │
    ┌──────────▼──────────┐
    │    Read Database    │
    │  (Denormalized DB)  │
    └─────────────────────┘

================================================================================
5. SIMPLE CQRS (SINGLE DATABASE)
================================================================================

DESCRIPTION:
------------
The simplest form of CQRS uses a SINGLE database but separates the read and
write logic in code — different models, different services, same underlying DB.

STRUCTURE:
----------
  [ Client ]
      |         \
  [Command        [Query
   Handler]        Handler]
      |                \
  [Write Model]    [Read Model]
      |                \
      └─────────────────┘
              |
         [ Single DB ]

WHEN TO USE:
------------
- Transitioning from a traditional CRUD app to CQRS
- When you need logical separation but not yet physical separation
- Small to medium applications

EXAMPLE:
--------
An order management system:
  - CommandService.placeOrder(command) → validates → updates Orders table
  - QueryService.getOrdersByUser(query) → reads from Orders table with joins

The same database is used, but write operations go through validation-heavy
domain models, while read operations use lightweight DTO projections.

LIMITATION:
-----------
Both read and write compete for the same DB resources. No independent scaling.

================================================================================
6. FULL CQRS (SEPARATE READ & WRITE DATABASES)
================================================================================

DESCRIPTION:
------------
Full CQRS physically separates the read and write databases. The write side uses
a normalized relational database optimized for consistency. The read side uses a
denormalized database optimized for fast queries (could be NoSQL, Redis, or
Elasticsearch).

STRUCTURE:
----------
  WRITE SIDE                         READ SIDE
  ──────────────────────────────────────────────────────
  [ Command Handler ]                [ Query Handler ]
         |                                   |
  [ Domain Model ]                   [ Read Model / DTO ]
         |                                   |
  [ Write DB (PostgreSQL) ]         [ Read DB (MongoDB/Redis) ]
         |
  [ Domain Event Emitted ]
         |
  [ Event Handler / Projector ]
         |
  [ Updates Read DB ]
  ──────────────────────────────────────────────────────

SYNCHRONIZATION:
----------------
When a command changes the write database, a domain event is emitted. An
event handler (projector) listens to this event and updates the read database.
This introduces EVENTUAL CONSISTENCY (the read model is slightly behind the
write model for a brief period).

EXAMPLE:
--------
E-Commerce Platform:
  Write DB: PostgreSQL
    - Orders table (normalized, with foreign keys to Users, Products)
    - OrderItems table
    - Payments table

  Read DB: MongoDB
    - orders_view collection (denormalized document per order):
      {
        orderId: "123",
        customerName: "Alice",
        customerEmail: "alice@example.com",
        items: [
          { product: "Laptop", qty: 1, price: 75000 }
        ],
        totalAmount: 75000,
        status: "Processing",
        createdAt: "2024-01-15"
      }

  The MongoDB document is pre-joined and ready to serve in a single query —
  no expensive SQL JOINs needed at read time.

7. CQRS + EVENT SOURCING
================================================================================

DESCRIPTION:
------------
CQRS is frequently combined with Event Sourcing (ES). While CQRS separates
read and write models, Event Sourcing changes HOW STATE IS STORED on the
write side — instead of storing the current state, you store the sequence of
events that led to the current state.

EVENT SOURCING CONCEPT:
-----------------------
Traditional storage:  Store the CURRENT STATE of an entity
  Order { id: 1, status: "Shipped", total: 5000 }

Event Sourcing storage: Store the SEQUENCE OF EVENTS
  1. OrderCreated    { orderId: 1, total: 5000, timestamp: T1 }
  2. PaymentReceived { orderId: 1, amount: 5000, timestamp: T2 }
  3. OrderShipped    { orderId: 1, trackingId: "ABC", timestamp: T3 }

To get the current state, you REPLAY the events from the beginning.

COMBINED CQRS + EVENT SOURCING FLOW:
-------------------------------------
  1. Client sends PlaceOrderCommand
  2. Command Handler validates and processes it
  3. Domain Model (Aggregate) produces an OrderPlacedEvent
  4. Event is stored in the Event Store (append-only log)
  5. Event is also published to an event bus
  6. Projector/Event Handler receives the event
  7. Projector updates the Read Model (View DB)
  8. Query Handler reads from the View DB

STRUCTURE:
----------
  [ Command ] → [ Aggregate ] → [ Event Store ] → [ Event Bus ]
                                                         |
                                                 [ Projector ]
                                                         |
                                                  [ Read DB ]
                                                         |
                                                  [ Query Handler ]

BENEFITS OF COMBINING:
-----------------------
+ Complete audit trail — every state change is recorded as an event
+ Time travel — reconstruct state at any point in time
+ Rebuild read models — replay events to create new projections/views
+ Debugging — see exactly what happened and when
+ Event replay — reprocess historical events with new business logic

EXAMPLE:
--------
Banking System:
  Events stored in Event Store for Account #42:
    AccountOpened    { accountId: 42, ownerId: 5, balance: 0 }
    MoneyDeposited   { accountId: 42, amount: 10000 }
    MoneyWithdrawn   { accountId: 42, amount: 3000 }
    MoneyDeposited   { accountId: 42, amount: 5000 }

  Current balance = replay: 0 + 10000 - 3000 + 5000 = 12000
  Read model stores: { accountId: 42, balance: 12000 }

================================================================================
8. CQRS + MICROSERVICES
================================================================================

DESCRIPTION:
------------
CQRS pairs naturally with microservices. Each microservice may implement its
own CQRS pattern internally, maintaining separate read and write models.
Services communicate asynchronously through events.

STRUCTURE:
----------
  ┌────────────────────────────────────────────────────┐
  │               Order Service                         │
  │  [OrderCommandHandler]   [OrderQueryHandler]        │
  │  [Write DB: PostgreSQL]  [Read DB: MongoDB]         │
  └─────────────────┬──────────────────────────────────┘
                    │  OrderPlacedEvent
          ┌─────────▼──────────┐
          │   Event Bus        │
          │   (Kafka/RabbitMQ) │
          └───┬────────────────┘
              │                   │
  ┌───────────▼──────┐   ┌────────▼────────────┐
  │ Inventory Service│   │ Notification Service │
  │ (consumes event) │   │ (consumes event)     │
  │ [CQRS internally]│   │ [sends email/SMS]    │
  └──────────────────┘   └─────────────────────┘

KEY POINTS:
-----------
- Each service owns its own read and write models
- No shared database between services (Database per Service pattern)
- Services are decoupled — they communicate only through events
- Each service can choose its own read/write database technology

================================================================================
9. DATA FLOW — STEP-BY-STEP WALKTHROUGH
================================================================================

SCENARIO: User places an order on an e-commerce platform

WRITE SIDE FLOW (Command):
--------------------------
Step 1:  User clicks "Place Order" on the UI
Step 2:  UI sends HTTP POST to the API Gateway
         POST /orders
         Body: { userId: 5, productId: 101, quantity: 2 }

Step 3:  API Gateway routes to Order Command Service
Step 4:  PlaceOrderCommand is created:
         PlaceOrderCommand { userId: 5, productId: 101, quantity: 2 }

Step 5:  Command Handler receives the command and:
         a. Validates: Is the user authenticated? Is product in stock?
         b. Loads the Order Aggregate from the write database
         c. Calls aggregate.placeOrder(command)

Step 6:  Order Aggregate:
         a. Applies business rules (stock check, fraud check)
         b. Generates a domain event: OrderPlacedEvent
            { orderId: 999, userId: 5, productId: 101, qty: 2, total: 4000 }
         c. Saves the new order record to Write DB (PostgreSQL)

Step 7:  OrderPlacedEvent is published to the Event Bus (Kafka)

Step 8:  Command Handler returns 202 Accepted (or orderId) to the client

READ SIDE SYNC FLOW (Projection):
----------------------------------
Step 9:  Event Handler / Projector listens on Kafka for OrderPlacedEvent
Step 10: Projector receives OrderPlacedEvent
Step 11: Projector builds a denormalized Order view document:
         {
           orderId: 999,
           customerName: "Alice",
           items: [{ product: "Wireless Mouse", qty: 2, price: 4000 }],
           status: "Processing",
           total: 4000,
           createdAt: "2024-05-01T10:30:00Z"
         }
Step 12: Projector writes this document to Read DB (MongoDB)

QUERY SIDE FLOW:
----------------
Step 13: User navigates to "My Orders" page
Step 14: UI sends HTTP GET to the API Gateway
         GET /orders?userId=5

Step 15: API Gateway routes to Order Query Service
Step 16: GetOrdersByUserQuery { userId: 5 } is created
Step 17: Query Handler fetches pre-built view from MongoDB:
         db.orders_view.find({ userId: 5 })
Step 18: Returns list of orders instantly (no JOINs, no heavy computation)
Step 19: UI renders the order list

10. EVENTUAL CONSISTENCY IN CQRS
================================================================================

WHAT IS IT?
-----------
In Full CQRS with separate databases, after a command is processed and the
write database is updated, the read database is NOT updated instantly. There
is a brief delay (milliseconds to seconds) while the event propagates and the
projector updates the read model. This is called EVENTUAL CONSISTENCY.

TIMELINE:
---------
  T=0ms:   PlaceOrderCommand processed, Write DB updated
  T=5ms:   OrderPlacedEvent published to Kafka
  T=20ms:  Projector receives event, updates Read DB
  T=25ms:  Query to Read DB now returns updated order

  During T=0ms to T=20ms: Read DB is STALE (doesn't show new order yet)

IS THIS A PROBLEM?
------------------
Usually NO. Most real-world systems naturally tolerate a small delay. Users
don't expect to see their order in the history list the exact millisecond
they click "Place Order." A confirmation message handles this gracefully.

HANDLING STRATEGIES:
--------------------
1. Optimistic UI: Show the result in the UI immediately based on the command
   response, without waiting for the read model to update.

2. Wait for Sync: Return a token/version to the client; client polls until the
   read model has caught up.

3. Read from Write: For critical operations immediately after a command, read
   directly from the write database once, then switch to the read model.

4. Versioning: Attach a version number to read model documents; clients can
   request a minimum version.

================================================================================
11. READ MODEL (PROJECTIONS) — DEEP DIVE
================================================================================

WHAT IS A READ MODEL?
---------------------
The Read Model (also called a Projection or View Model) is a pre-computed,
denormalized representation of data, specifically optimized for how the client
wants to READ the data — not how it's stored.

PURPOSE:
--------
- Eliminate expensive JOIN queries at read time
- Serve queries in a single database lookup
- Tailor data shape exactly to what the UI/client needs
- Can have multiple read models for the same data (different views)

MULTIPLE PROJECTIONS FROM THE SAME EVENTS:
-------------------------------------------
The same domain events can populate MULTIPLE read models simultaneously,
each serving a different use case:

  OrderPlacedEvent triggers:
    → CustomerOrdersProjection  (for "My Orders" page)
    → AdminOrderDashboard       (for admin panel)
    → RevenueReportProjection   (for analytics dashboard)
    → InventoryProjection       (for stock management)

Each projection is shaped differently, stored in a different collection/table,
and optimized for its specific query pattern.

REBUILDING PROJECTIONS:
-----------------------
One of the most powerful features of CQRS + Event Sourcing:
If you need to change the shape of a read model or add a new one, you can:
  1. Create the new projection handler
  2. Replay all historical events from the Event Store
  3. The new read model is populated from scratch
No data migration scripts needed!

EXAMPLE — Different Read Models for Order:
-------------------------------------------
CustomerOrdersProjection (MongoDB):
  { orderId, productName, qty, total, status, createdAt }
  → Optimized for customer-facing "My Orders" list

AdminOrderView (Elasticsearch):
  { orderId, customerId, customerEmail, products[], total, fraudScore, status }
  → Optimized for admin search and filtering across millions of orders

RevenueReport (Redis):
  { date: "2024-05-01", totalRevenue: 850000, orderCount: 320 }
  → Optimized for real-time dashboard display

================================================================================
12. WRITE MODEL (AGGREGATES) — DEEP DIVE
================================================================================

WHAT IS AN AGGREGATE?
---------------------
In CQRS (especially with Domain-Driven Design), the Write Model is organized
around Aggregates. An Aggregate is a cluster of domain objects (entities and
value objects) that are treated as a single unit for data changes.

KEY PROPERTIES:
---------------
- Has a single Aggregate Root (the main entity)
- All changes go through the Aggregate Root
- Enforces business invariants (rules that must always be true)
- Emits Domain Events when state changes

EXAMPLE — Order Aggregate:
---------------------------
  OrderAggregate (Aggregate Root: Order entity)
    ├── Order       (root entity: id, status, total)
    ├── OrderItems  (child entities: productId, qty, price)
    └── ShippingAddress (value object: street, city, pincode)

  Business Invariants enforced by OrderAggregate:
    - An order must have at least one item
    - Total must equal sum of (qty × price) for all items
    - Cannot ship an order that hasn't been paid
    - Cannot cancel an order that is already delivered

AGGREGATE BEHAVIOR (COMMANDS → EVENTS):
-----------------------------------------
  Command: PlaceOrderCommand
    → Aggregate validates: stock available? user is valid? 
    → Aggregate emits: OrderPlacedEvent
    → State changes: order.status = "Placed"

  Command: CancelOrderCommand
    → Aggregate validates: is order in cancellable state?
    → If order is "Delivered" → throws OrderCannotBeCancelledException
    → Aggregate emits: OrderCancelledEvent
    → State changes: order.status = "Cancelled"

13. MEDIATOR PATTERN IN CQRS
================================================================================

DESCRIPTION:
------------
The Mediator Pattern is commonly used to implement CQRS in code. Instead of
services calling each other directly, all Commands and Queries are sent to a
central Mediator, which routes them to the appropriate Handler.

FLOW:
-----
  [ Controller ] → sends Command/Query to → [ Mediator ]
                                                  |
                                 ┌────────────────┴──────────────────┐
                                 ▼                                   ▼
                     [ Command Handler ]                  [ Query Handler ]

BENEFITS:
---------
+ Decouples controllers from business logic
+ Single entry point for all operations
+ Easy to add cross-cutting concerns (logging, validation, caching) via Pipeline
+ Clean, maintainable code

POPULAR LIBRARIES:
------------------
- .NET: MediatR (by Jimmy Bogard) — most widely used CQRS library
- Java: Axon Framework — full CQRS + Event Sourcing framework
- Node.js: NestJS CQRS Module

PSEUDOCODE EXAMPLE:
-------------------
  // Controller — knows nothing about handlers
  class OrderController {
      post("/orders") {
          command = new PlaceOrderCommand(req.body)
          result = mediator.send(command)
          return result
      }

      get("/orders/:id") {
          query = new GetOrderByIdQuery(req.params.id)
          result = mediator.send(query)
          return result
      }
  }

  // Mediator routes automatically to the right handler
  mediator.send(PlaceOrderCommand)  → routes to → PlaceOrderCommandHandler
  mediator.send(GetOrderByIdQuery)  → routes to → GetOrderByIdQueryHandler

14. ADVANTAGES OF CQRS
================================================================================

1. INDEPENDENT SCALABILITY
   -----------------------
   Read and write sides can be scaled independently based on load.
   If reads are 100x more frequent than writes (typical for e-commerce),
   scale only the read side (add more read DB replicas, cache layers)
   without touching the write side.

2. OPTIMIZED PERFORMANCE
   ----------------------
   Read models are denormalized and pre-computed. Queries return data in
   a single lookup without expensive JOINs or complex aggregations.
   Write models are normalized for consistency and integrity.

3. SIMPLIFIED MODELS
   ------------------
   Each model is simpler because it only does one thing.
   Read models don't carry mutation logic; write models don't carry
   display/formatting logic.

4. FLEXIBILITY IN STORAGE
   -----------------------
   Use the best database for each job:
   - Write side: PostgreSQL (ACID transactions, referential integrity)
   - Read side: MongoDB (flexible schema), Redis (cache), Elasticsearch (search)

5. IMPROVED SECURITY
   ------------------
   Easy to enforce that the read side has read-only database credentials.
   Commands can have fine-grained authorization at the handler level.

6. AUDIT TRAIL & HISTORY
   ----------------------
   When combined with Event Sourcing, every change is recorded as an
   immutable event — perfect for compliance, debugging, and auditing.

7. ENABLES COMPLEX DOMAIN LOGIC
   ------------------------------
   The write side can be enriched with Domain-Driven Design (DDD) patterns —
   Aggregates, Domain Events, Invariants — without polluting the read side.

8. SUPPORTS MULTIPLE VIEWS
   -------------------------
   Same data can have multiple read models for different clients:
   mobile app, web app, analytics, admin panel — each optimized differently.

================================================================================
15. DISADVANTAGES & CHALLENGES
================================================================================

1. INCREASED COMPLEXITY
   ---------------------
   Two models, two databases (potentially), event handling, projections —
   significantly more moving parts than a simple CRUD application.
   Requires a team with good understanding of the pattern.

2. EVENTUAL CONSISTENCY
   ---------------------
   Read model lags behind write model. Must handle and communicate this
   to users. Not suitable where data must be immediately consistent
   (e.g., financial ledgers requiring immediate balance reads).

3. INFRASTRUCTURE OVERHEAD
   -------------------------
   Requires an event bus (Kafka, RabbitMQ), possibly an Event Store,
   separate databases, projection services. Increased DevOps complexity.

4. LEARNING CURVE
   ---------------
   Developers unfamiliar with CQRS, DDD, or Event Sourcing face a steep
   learning curve. Team training and discipline are required.

5. RISK OF OVER-ENGINEERING
   -------------------------
   Applying CQRS to a simple CRUD application is overkill and results
   in unnecessary complexity with little benefit.

6. DATA SYNCHRONIZATION ISSUES
   -----------------------------
   If the projector fails or has a bug, the read model gets out of sync
   with the write model. Requires monitoring, retry logic, and the ability
   to rebuild projections.

7. DEBUGGING DIFFICULTY
   ---------------------
   Tracing a request across command handler → event store → event bus →
   projector → read model requires distributed tracing tools.

================================================================================
16. WHEN TO USE CQRS
================================================================================

USE CQRS WHEN:
--------------
✓ Read and write workloads have significantly different scaling needs
  (e.g., 1000 reads per second but only 10 writes per second)

✓ Read queries are complex (multiple JOINs, aggregations, full-text search)
  and would benefit from a pre-built, denormalized view

✓ The application has complex business rules that require rich domain models
  on the write side (DDD-heavy applications)

✓ You need a complete audit trail or history of all changes (combine with ES)

✓ Multiple different views of the same data are needed by different clients

✓ Different teams work on read and write sides independently

✓ Collaboration-intensive domains where write conflicts must be managed
  (booking systems, inventory management, financial transactions)

✓ You're already using an event-driven microservices architecture

================================================================================
17. WHEN NOT TO USE CQRS
================================================================================

DO NOT USE CQRS WHEN:
---------------------
✗ Simple CRUD applications — if your app is just create/read/update/delete
  with simple queries, CQRS adds unnecessary complexity

✗ Small team with limited distributed systems experience

✗ Domain logic is simple — no complex business rules or invariants

✗ Strong consistency is required — if you cannot tolerate any delay
  between a write and its visibility in reads

✗ Early-stage startup / MVP — get to market first; refactor later

✗ The application is small and unlikely to grow significantly

RULE OF THUMB:
--------------
Start with a simple layered architecture or modular monolith. Introduce CQRS
only when you encounter a concrete problem it solves — not preemptively.

18. CQRS vs TRADITIONAL CRUD
================================================================================

ASPECT              | TRADITIONAL CRUD           | CQRS
--------------------+----------------------------+-------------------------------
Data Model          | Single model for R/W        | Separate models for R and W
Database            | One DB for everything        | Separate DBs (optional)
Read Performance    | Requires JOINs at query time | Pre-built denormalized views
Write Logic         | Mixed with read logic        | Isolated in Command Handlers
Complexity          | Low                          | High
Scalability         | Limited (same DB for R/W)    | High (scale R/W independently)
Consistency         | Immediate (ACID)             | Eventual (with separate DBs)
Audit Trail         | Requires separate logging    | Natural with Event Sourcing
Best For            | Simple apps, small teams     | Complex, high-traffic domains
Learning Curve      | Low                          | High

CRUD EXAMPLE:
-------------
  // CRUD — same model, same DB for everything
  OrderService.getOrder(id)         → SELECT * FROM orders WHERE id = ?
  OrderService.placeOrder(data)     → INSERT INTO orders ...
  OrderService.updateStatus(id, s)  → UPDATE orders SET status = ? WHERE id = ?

CQRS EXAMPLE:
-------------
  // CQRS — separate paths
  mediator.send(new PlaceOrderCommand(data))    → Command Handler → Write DB
  mediator.send(new GetOrderQuery(id))          → Query Handler  → Read DB

================================================================================
19. CQRS vs EVENT SOURCING (DIFFERENCES)
================================================================================

THEY ARE DIFFERENT PATTERNS (but often used together):

CQRS:
-----
- About SEPARATING READ and WRITE responsibilities
- Doesn't dictate HOW state is stored
- You can have CQRS without Event Sourcing
- Answers: "How do we handle read vs write operations?"

EVENT SOURCING:
---------------
- About HOW STATE IS PERSISTED (as a log of events)
- Doesn't require CQRS
- You can have Event Sourcing without CQRS
- Answers: "How do we store state changes?"

TOGETHER:
---------
They complement each other naturally:
- CQRS defines the separate read/write models
- Event Sourcing provides the event log as the source of truth for the write model
- Events from Event Sourcing are used to populate the CQRS read model

ANALOGY:
--------
Think of a bank:
- Event Sourcing = the transaction ledger (every debit/credit recorded)
- CQRS = the bank statement (a pre-built summary view for customers to read)

20. REAL-WORLD EXAMPLES
================================================================================

1. AMAZON — E-Commerce Orders
   ---------------------------
   - Commands: PlaceOrder, CancelOrder, ReturnOrder
   - Write DB: Normalized relational DB with full business logic
   - Read DB: Denormalized product/order views per user
   - Events: "OrderPlaced" triggers Inventory, Billing, Notification services
   - Result: Millions of concurrent reads served from pre-built views

2. NETFLIX — Content Platform
   ---------------------------
   - Commands: AddToWatchlist, RateContent, UpdateProfile
   - Queries: GetRecommendations, GetWatchlist, GetContentDetails
   - Each service owns its CQRS implementation
   - Read models are heavily cached with multiple layers (Redis, CDN)

3. BANKING SYSTEMS
   ----------------
   - Commands: Deposit, Withdraw, Transfer
   - Write side: Event Sourcing for complete transaction history
   - Read side: Account balance view, transaction history view
   - Complete audit trail satisfies regulatory requirements

4. RIDE-HAILING (UBER / OLA)
   --------------------------
   - Commands: RequestRide, CancelRide, CompleteRide
   - Queries: GetNearbyDrivers, GetRideHistory, GetPriceEstimate
   - Read model for "nearby drivers" uses geospatial index (Redis GEO)
   - Write model handles ride lifecycle with strict state machine

5. SOCIAL MEDIA (TWITTER/X)
   -------------------------
   - Commands: PostTweet, FollowUser, LikeTweet
   - Queries: GetTimeline, GetTrending, GetUserProfile
   - Timeline is a read model — pre-computed fan-out of followed users' tweets
   - Writing a tweet (command) triggers fan-out to millions of followers' feeds

SCENARIO: Simple Order System with CQRS

-- COMMANDS & QUERIES (Data Transfer Objects) ---

  class PlaceOrderCommand:
      userId: string
      productId: string
      quantity: int

  class GetOrderByIdQuery:
      orderId: string

-- COMMAND HANDLER ---

  class PlaceOrderCommandHandler:
      handle(command: PlaceOrderCommand):
          // 1. Validate
          user = userRepository.findById(command.userId)
          if not user: throw UserNotFoundException

          product = productRepository.findById(command.productId)
          if product.stock < command.quantity: throw InsufficientStockException

          // 2. Create domain model
          order = new Order(
              id: generateId(),
              userId: command.userId,
              productId: command.productId,
              quantity: command.quantity,
              total: product.price * command.quantity,
              status: "Placed"
          )

          // 3. Save to Write DB
          orderWriteRepository.save(order)

          // 4. Emit domain event
          eventBus.publish(new OrderPlacedEvent(order))

          return order.id

-- QUERY HANDLER ---

  class GetOrderByIdQueryHandler:
      handle(query: GetOrderByIdQuery):
          // Fetch directly from Read DB — no joins needed
          orderView = orderReadRepository.findById(query.orderId)
          if not orderView: throw OrderNotFoundException
          return orderView

-- EVENT HANDLER (PROJECTOR) ---

  class OrderProjector:
      on(event: OrderPlacedEvent):
          // Build denormalized read model
          user = userReadStore.get(event.userId)
          product = productReadStore.get(event.productId)

          orderView = {
              orderId:       event.orderId,
              customerName:  user.name,
              customerEmail: user.email,
              productName:   product.name,
              quantity:      event.quantity,
              total:         event.total,
              status:        "Placed",
              createdAt:     event.timestamp
          }

          // Save to Read DB
          orderReadRepository.save(orderView)

-- API CONTROLLER ---

  class OrderController:
      POST /orders:
          command = PlaceOrderCommand(req.body)
          orderId = mediator.send(command)
          return { orderId: orderId, status: "Order placed successfully" }

      GET /orders/:id:
          query = GetOrderByIdQuery(req.params.id)
          orderView = mediator.send(query)
          return orderView


================================================================================
KEY TERMINOLOGY GLOSSARY
================================================================================
TERM                    DEFINITION
----------------------- --------------------------------------------------------
CQRS                    Command Query Responsibility Segregation — separates
                        read and write operations into distinct models

Command                 An intent to change state (e.g., PlaceOrderCommand).
                        Does not return business data.

Query                   A request to read state (e.g., GetOrderQuery).
                        Never modifies state.

Command Handler         Class/function that processes a specific Command.
                        Contains business logic for the write side.

Query Handler           Class/function that processes a specific Query.
                        Fetches data from the read model.

Write Model             The domain model used for processing commands.
                        Typically normalized, enforces business rules.

Read Model              Pre-built, denormalized view of data optimized for
                        queries. Also called Projection or View Model.

Projection              The process or result of building a read model from
                        domain events. Each projection serves a specific use case.

Domain Event            A record of something that has happened in the domain.
                        (e.g., OrderPlacedEvent, PaymentCompletedEvent)

Event Store             Append-only storage for domain events (used with ES).

Event Sourcing (ES)     Storing state as a sequence of events rather than
                        current state. Often combined with CQRS.

Aggregate               A cluster of domain objects treated as a unit for
                        data changes. Has an Aggregate Root.

Aggregate Root          The main entity in an Aggregate through which all
                        changes must be made.

Mediator                A design pattern that routes Commands/Queries to their
                        respective Handlers without direct coupling.

Eventual Consistency    The state where the read model may temporarily lag
                        behind the write model, but will eventually catch up.

CQS                     Command Query Separation — the method-level predecessor
                        to CQRS (by Bertrand Meyer).

Denormalization         Intentional redundancy in a read model — data is
                        pre-joined and stored together for fast retrieval.

Fan-out                 Writing an event's result to many read model records
                        (e.g., publishing a tweet updates all followers' timelines).

Projector               A component that listens to domain events and updates
                        the read model accordingly.

Event Bus               Middleware that transports events between producers and
                        consumers (Kafka, RabbitMQ, AWS SNS).

Idempotent Handler      A handler that produces the same result even if the
                        same event is processed multiple times — essential for
                        safe event replay.

Saga                    A sequence of Commands and Events that coordinate a
                        long-running business transaction across multiple services.
