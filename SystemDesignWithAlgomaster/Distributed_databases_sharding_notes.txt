================================================================================
        DISTRIBUTED DATABASES & AUTOMATIC SHARDING
================================================================================
================================================================================
1. WHAT IS A DISTRIBUTED DATABASE?
================================================================================
A distributed database is a database where data is stored across multiple physical machines (nodes), yet appears to users and applications as a single logical database. Unlike a traditional single-node RDBMS (e.g., PostgreSQL, MySQL running on one server), a distributed database:

  - Splits data horizontally across multiple nodes (sharding).
  - Replicates data across nodes for fault tolerance.
  - Coordinates queries and transactions that span multiple nodes.
  - Scales horizontally — adding more nodes increases capacity and throughput.

Examples of distributed databases:
  - CockroachDB       (NewSQL, PostgreSQL-compatible)
  - Vitess            (MySQL sharding middleware)
  - Google Spanner    (Google's globally distributed RDBMS)
  - Amazon Aurora     (Cloud-native distributed MySQL/PostgreSQL)
  - TiDB              (MySQL-compatible NewSQL)
  - Cassandra         (NoSQL, wide-column)
  - MongoDB           (NoSQL, document)
  - YugabyteDB        (PostgreSQL-compatible)


================================================================================
2. THE PROBLEM: WHY SINGLE-NODE DATABASES FALL SHORT
================================================================================

A single-node database hits physical ceilings:

  a) STORAGE LIMIT
     A single machine has finite disk. A 10TB database on a single machine means you cannot grow beyond the disk capacity without expensive upgrades.

  b) WRITE THROUGHPUT LIMIT
     All writes funnel through one CPU, one disk I/O path. At high write loads (e.g., millions of writes/second), the single node becomes a bottleneck.

  c) READ THROUGHPUT LIMIT
     Even with read replicas, all writes still go to one primary. Read scaling has limits when data is huge and queries are complex.

  d) SINGLE POINT OF FAILURE
     If the one machine crashes, the entire database goes down.

  e) LATENCY FOR GLOBAL USERS
     Data sitting in one data center (e.g., US-East) means high latency for users in Europe or Asia.

Solution: Distribute data across many nodes — sharding.


================================================================================
3. SHARDING — THE CORE CONCEPT
================================================================================
Sharding = Horizontal partitioning of data across multiple database nodes.

Each partition is called a "shard." Every shard contains a subset of the total data. Together, all shards hold the complete dataset.

Example:
  - Users table with 100 million rows.
  - Shard 1: users with id 1        – 25,000,000
  - Shard 2: users with id 25000001 – 50,000,000
  - Shard 3: users with id 50000001 – 75,000,000
  - Shard 4: users with id 75000001 – 100,000,000

Each shard lives on its own node (or set of nodes for replication).

----- 3.1 MANUAL SHARDING -----

With traditional databases (MySQL, PostgreSQL), sharding is done manually:

  - The application layer decides which shard to read/write from.
  - Developers write custom routing logic (e.g., "user_id % 4 => shard").
  - Schema changes must be applied to every shard separately.
  - Cross-shard queries (JOINs across shards) must be handled in application.
  - Adding new shards requires manual data migration.

Problems with manual sharding:
  - High operational complexity.
  - Application code becomes tightly coupled to shard topology.
  - Rebalancing data when adding nodes is painful and error-prone.
  - Cross-shard transactions are extremely hard to implement correctly.

----- 3.2 AUTOMATIC SHARDING -----

Modern distributed databases like CockroachDB and Vitess handle sharding automatically at the database layer:

  - The database decides how to partition data.
  - The database routes queries to the correct shard(s) transparently.
  - Adding nodes triggers automatic rebalancing.
  - The application sees a single logical database (no shard-awareness needed).
  - Cross-shard queries are handled internally.


================================================================================
4. HOW AUTOMATIC SHARDING WORKS (INTERNALS)
================================================================================

----- 4.1 DATA PARTITIONING STRATEGIES -----

There are two primary strategies for deciding which rows go to which shard:

  A) HASH-BASED PARTITIONING
     - Apply a hash function to the partition key (e.g., user_id).
     - Use hash value to determine the shard.
     - Formula: shard = hash(key) % num_shards
     - Pros: Even data distribution; avoids hotspots.
     - Cons: Range queries are inefficient (scatter across all shards);
             rebalancing requires remapping many keys.

  B) RANGE-BASED PARTITIONING
     - Divide the key space into contiguous ranges; each range → one shard.
     - Example: keys 0–999 → Shard 1, keys 1000–1999 → Shard 2, etc.
     - Pros: Efficient range scans (single shard often handles the range).
     - Cons: Risk of hotspots if keys are not uniformly distributed (e.g., monotonically increasing IDs all land on the last shard).

  C) DIRECTORY-BASED PARTITIONING
     - A lookup table (directory service) maps each key to its shard.
     - Very flexible but the directory becomes a bottleneck and single point of failure if not carefully managed.

CockroachDB uses range-based partitioning.
Vitess supports hash and range-based sharding depending on configuration.

----- 4.2 CONSISTENT HASHING -----

Consistent hashing is a technique used in distributed systems to minimize data movement when nodes are added or removed.

  - Keys and nodes are mapped to positions on a virtual "ring."
  - Each key belongs to the nearest node clockwise on the ring.
  - When a node is added: only keys between the new node and its predecessor need to move. (Contrast: naive hashing moves ~N/M keys when M nodes change.)
  - When a node is removed: its keys are transferred to the next node.

Used heavily in Cassandra, DynamoDB. CockroachDB uses a variant with ranges.

----- 4.3 RANGE-BASED PARTITIONING (CockroachDB's approach) -----

CockroachDB stores all data in a single sorted key-value store. The key space is divided into ranges (called "ranges" in CockroachDB, default ~512MB each).

  - Every row is encoded as a key-value pair.
  - Key = (table_id, index_id, primary_key_columns...)
  - The key space is sorted lexicographically.
  - Contiguous key ranges are assigned to range replicas.
  - Each range is replicated across 3 (or 5) nodes via Raft.

This means:
  - Range scans are efficient (sequential read within a range).
  - The system automatically splits ranges that grow too large.
  - Ranges are automatically merged if they shrink (after deletes).

----- 4.4 REBALANCING / RE-SHARDING -----

When nodes are added or removed, data must be redistributed:

  CockroachDB:
    - The rebalancer runs continuously in the background.
    - It identifies over-loaded ranges and moves replica leadership.
    - Snapshots of range data are streamed to new nodes.
    - No application downtime; the process is incremental.

  Vitess:
    - Horizontal resharding is an explicit operation.
    - Vitess copies data, validates consistency, then switches over traffic.
    - The resharding workflow is orchestrated by a tool called `vtctldclient`.
    - During resharding, both old and new shards serve traffic until cutover.


================================================================================
5. COCKROACHDB — DEEP DIVE
================================================================================

CockroachDB is a cloud-native, distributed SQL database designed to:
  - Survive hardware failures (resilience like a cockroach — hence the name).
  - Scale horizontally across nodes and data centers.
  - Provide full ACID transactions across the entire distributed cluster.
  - Be wire-compatible with PostgreSQL (apps can use existing PG drivers).

----- 5.1 ARCHITECTURE -----

CockroachDB is a shared-nothing architecture. Every node is identical and can accept reads and writes. There is no single master.

  ┌─────────────────────────────────────────────────┐
  │                  SQL Layer                      │  ← Parses SQL, plans queries
  ├─────────────────────────────────────────────────┤
  │           Transaction Layer (KV)                │  ← MVCC, locking, Raft
  ├─────────────────────────────────────────────────┤
  │          Distribution Layer                     │  ← Range routing, replication
  ├─────────────────────────────────────────────────┤
  │          Storage Layer (Pebble LSM)             │  ← Actual disk storage
  └─────────────────────────────────────────────────┘

  Nodes communicate via gRPC (HTTP/2 + Protocol Buffers).

----- 5.2 HOW IT SHARDS AUTOMATICALLY -----

Step-by-step flow of automatic sharding in CockroachDB:

  1. Data is stored as key-value pairs in a sorted key space.
  2. The key space is split into ranges (~512MB each by default).
  3. Each range is replicated to N nodes (default N=3) using Raft consensus.
  4. One replica per Raft group is the "leaseholder" — it serves reads & writes.
  5. A background goroutine monitors range sizes.
  6. When a range exceeds the size threshold → automatic SPLIT into two ranges.
  7. The rebalancer moves replicas to ensure even distribution across nodes.
  8. When nodes are added: new node registers, rebalancer migrates ranges to it.
  9. When nodes die: Raft detects missing replica, a new one is up-replicated
     elsewhere within the cluster.

The application sends queries to any node. That node acts as a gateway:
  - It determines which ranges the query touches.
  - Routes sub-requests to the leaseholder nodes of those ranges.
  - Assembles results and returns to the client.

----- 5.3 REPLICATION & CONSENSUS (RAFT) -----

Raft is a consensus algorithm that ensures all replicas of a range agree on the same sequence of writes.

  - Each range has a Raft group (typically 3 or 5 replicas).
  - One replica is elected the "leader" (leaseholder in CockroachDB's terms).
  - All writes go through the leader, which proposes a log entry.
  - A write is committed only after a MAJORITY of replicas acknowledge it.
  - With 3 replicas: tolerates 1 failure (quorum = 2).
  - With 5 replicas: tolerates 2 failures (quorum = 3).

This guarantees:
  - No data loss if a minority of nodes fail.
  - The system remains operational (available for reads and writes) as long
    as a majority of replicas for each range are alive.

----- 5.4 TRANSACTIONS IN COCKROACHDB -----

CockroachDB provides full serializable ACID transactions across multiple ranges (and thus across multiple nodes).

Mechanism:
  - Uses Multi-Version Concurrency Control (MVCC): each row has multiple
    timestamped versions. Reads see a consistent snapshot without locking.
  - Transactions are assigned a timestamp from a Hybrid Logical Clock (HLC).
  - HLC combines physical time + logical counter to order events globally
    without requiring perfectly synchronized clocks.
  - Write intents: uncommitted writes are stored as "intents" in the KV store.
    Other transactions that encounter intents must wait or push the timestamp.
  - Commit: when the transaction commits, intents are resolved to actual values.
  - Conflict resolution: uses a "transaction record" stored in the KV store.

Isolation level: Serializable (highest ANSI SQL isolation level) by default.

----- 5.5 KEY FEATURES -----

  ✔ PostgreSQL wire protocol compatibility (psql, pg drivers, ORMs work).
  ✔ Automatic sharding and rebalancing.
  ✔ Multi-region deployments with locality-aware replica placement.
  ✔ Serializable transactions spanning multiple nodes.
  ✔ Follower reads (stale reads served from local replicas — lower latency).
  ✔ Geo-partitioning: pin certain data to specific regions (for data residency).
  ✔ Online schema changes (no table locks on ALTER TABLE).
  ✔ Built-in backup to cloud storage (S3, GCS).
  ✔ Prometheus-compatible metrics, web UI for cluster monitoring.

6. VITESS — DEEP DIVE
================================================================================

Vitess is an open-source database clustering system for horizontal scaling of MySQL. Originally built at YouTube (Google) to scale MySQL to millions of users, it was open-sourced and is now a CNCF (Cloud Native Computing Foundation) graduated project.

Vitess does NOT replace MySQL — it wraps and orchestrates MySQL instances.

----- 6.1 ARCHITECTURE -----

  ┌──────────────────────────────────────────────────────────────┐
  │  Application                                                 │
  └──────────────────────┬───────────────────────────────────────┘
                         │ MySQL protocol
  ┌──────────────────────▼───────────────────────────────────────┐
  │  VTGate  (stateless proxy layer — query routing)             │
  └──────────────────────┬───────────────────────────────────────┘
                         │ gRPC
  ┌──────────────────────▼───────────────────────────────────────┐
  │  VTTablet (per-MySQL process — query serving, replication)   │
  └──────────────────────┬───────────────────────────────────────┘
                         │
  ┌──────────────────────▼───────────────────────────────────────┐
  │  MySQL / MariaDB instances (actual data storage)             │
  └──────────────────────────────────────────────────────────────┘

  Plus:
  ┌──────────────────────────────────────────────────────────────┐
  │  Topology Service (etcd or ZooKeeper) — cluster metadata     │
  │  vtctld — admin service for cluster operations               │
  └──────────────────────────────────────────────────────────────┘

Components:
  - VTGate: The entry point. Clients connect here using MySQL protocol.
            Routes queries to the correct shard(s). Handles cross-shard queries.
  - VTTablet: Runs alongside each MySQL instance. Manages replication,
              semi-sync, health checks, connection pooling, and query rules.
  - Topology Service: Stores cluster metadata (shard map, tablet locations,
                      schema info). Uses etcd or ZooKeeper as backend.
  - vtctld: HTTP server + gRPC service for administrative operations
            (resharding, reparenting, schema changes).

----- 6.2 HOW IT SHARDS AUTOMATICALLY -----

Vitess sharding flow:

  1. Define a keyspace (logical database) and a sharding key (e.g., user_id).
  2. Define shards: e.g., keyspace divided into 8 shards (-80 and 80-). (Vitess uses hex ranges: 0x00–0x80 = first half, 0x80–0xFF = second half.)
  3. VTGate receives a query from the application.
  4. VTGate inspects the query's WHERE clause to extract the sharding key value.
  5. It hashes the key and maps it to the correct shard via the VSchema rules.
  6. VTGate forwards the query to the VTTablet(s) of the target shard.
  7. VTTablet executes the query against its MySQL instance.
  8. For cross-shard queries (e.g., no WHERE on shard key), VTGate fans out
     the query to all shards and merges results (scatter-gather).

Important: Vitess's "automatic" sharding means the routing is automatic once the schema/sharding rules are configured. The initial sharding topology and re-sharding still require explicit operations (unlike CockroachDB's fully transparent range-based approach).

----- 6.3 VSCHEMA & KEYSPACES -----

VSchema is Vitess's schema metadata that describes how data is sharded.

Keyspace:
  - A logical database. Can be unsharded (single MySQL) or sharded.
  - Each keyspace has its own sharding configuration.

VSchema concepts:
  - Sharding key (Primary Vindex): The column used to route queries.
    Example: user_id for a users table.
  - Vindex: A mapping function from column value → keyspace ID (shard location).
    Types: hash (for random distribution), unicode_loose_md5, etc.
  - Lookup Vindex: Secondary index that maps a non-shard-key column to the
    sharding key. Enables routing queries by non-primary key (e.g., email).

Example VSchema snippet:
  {
    "sharded": true,
    "vindexes": {
      "hash": { "type": "hash" }
    },
    "tables": {
      "users": {
        "column_vindexes": [
          { "column": "user_id", "name": "hash" }
        ]
      }
    }
  }

----- 6.4 QUERY ROUTING -----

VTGate handles three categories of queries:

  1. SINGLE-SHARD QUERIES
     The WHERE clause includes the sharding key with a specific value.
     VTGate hashes the value, identifies one shard, and routes there.
     Example: SELECT * FROM users WHERE user_id = 12345;

  2. SCATTER-GATHER QUERIES
     The sharding key is not in the WHERE clause (or is a range).
     VTGate sends the query to ALL shards and merges results.
     Example: SELECT COUNT(*) FROM users WHERE country = 'IN';
     (Expensive — avoid for latency-sensitive paths.)

  3. CROSS-SHARD TRANSACTIONS
     Vitess supports 2-phase commit for cross-shard transactions,
     but they are more expensive and have weaker guarantees than
     single-shard transactions. Design schemas to minimize these.

----- 6.5 KEY FEATURES -----

  ✔ MySQL protocol compatible (any MySQL client/ORM works).
  ✔ Connection pooling: multiplexes thousands of app connections into far
    fewer MySQL connections — huge scalability advantage.
  ✔ Query rewriting & sanitization: blocks dangerous queries (e.g., SELECT *
    without LIMIT that would scatter to all shards).
  ✔ Online schema changes via gh-ost or pt-online-schema-change integration.
  ✔ Automated failover with Orchestrator or Vitess's own reparenting.
  ✔ Backup and restore via xtrabackup or mysqldump.
  ✔ Resharding: split or merge shards with minimal downtime.
  ✔ Row-based replication: enforces MySQL replication integrity.
  ✔ VReplication: internal streaming replication engine used for resharding,
    cross-cluster backfills, and materialized views.
  ✔ Traffic throttling and query kill policies.
  ✔ Used in production at: YouTube, Slack, GitHub, PlanetScale, Square.

8. CAP THEOREM & DISTRIBUTED TRADE-OFFS
================================================================================
The CAP Theorem states that a distributed system can guarantee at most TWO of the following three properties simultaneously:

  C — CONSISTENCY    : Every read receives the most recent write (or an error).
  A — AVAILABILITY   : Every request receives a response (not an error), though it might not be the most recent write.
  P — PARTITION TOL. : The system continues operating even when network partitions (message loss) occur between nodes.

Since network partitions are unavoidable in real distributed systems, the
practical choice is between CP and AP:

  CP Systems: Prioritize Consistency over Availability during partitions.
    - Will refuse to serve reads/writes if they cannot guarantee consistency.
    - Examples: CockroachDB, Google Spanner, HBase, ZooKeeper.

  AP Systems: Prioritize Availability over Consistency during partitions.
    - Will serve reads/writes even if data may be stale.
    - Examples: Cassandra, CouchDB, DynamoDB (eventually consistent mode).

CockroachDB is CP: during a partition, if a range cannot achieve Raft quorum, it will refuse to serve writes for that range (returns an error).
Vitess inherits MySQL's characteristics — generally CP with MySQL replication, but with asynchronous replication there's a risk of serving stale data.

PACELC Extension:
  Beyond CAP, the PACELC theorem adds: even without partitions (E), there is a trade-off between Latency (L) and Consistency (C).
  CockroachDB accepts higher latency (due to Raft consensus) in exchange for strong consistency.

9. CONSISTENCY MODELS IN DISTRIBUTED DATABASES
================================================================================

From strongest to weakest:

  1. LINEARIZABILITY (Strict Consistency)
     Operations appear instantaneous and globally ordered. Any read after a write returns the new value. Highest guarantee, highest latency cost.

  2. SERIALIZABLE
     The result of any transaction execution is equivalent to some serial (sequential) execution of those transactions. No anomalies like dirty
     reads, non-repeatable reads, or phantom reads. CockroachDB provides this by default.

  3. SNAPSHOT ISOLATION
     Each transaction reads from a consistent snapshot at its start time. Prevents dirty and non-repeatable reads. Can have write skew anomalies.

  4. READ COMMITTED
     Reads see only committed data (no dirty reads). Allows non-repeatable reads. MySQL default. Vitess inherits this.

  5. EVENTUAL CONSISTENCY
     Given no new updates, all replicas will eventually converge to the same value. No timing guarantees. Used in Cassandra, DynamoDB.

For financial/critical systems: Serializable or Linearizability.
For high-throughput analytics: Read Committed or Snapshot Isolation.
For social feeds, caches: Eventual Consistency is often acceptable.

10. DISTRIBUTED TRANSACTIONS — THE HARD PROBLEM
================================================================================
Transactions that span multiple shards/nodes are the hardest problem in distributed databases.

----- 10.1 TWO-PHASE COMMIT (2PC) -----

2PC is the classic protocol for distributed transactions:

  Phase 1 — PREPARE:
    Coordinator sends "PREPARE" to all participant nodes.
    Each participant writes the transaction to a durable log and replies "YES" (ready to commit) or "NO" (abort).

  Phase 2 — COMMIT/ABORT:
    If all participants said "YES": Coordinator sends "COMMIT" to all.
    If any said "NO": Coordinator sends "ABORT" to all.
    Participants apply or roll back the transaction.

Problems with 2PC:
  - Blocking: If the coordinator crashes after Phase 1, participants are "in doubt" and must block (hold locks) until the coordinator recovers.
  - Performance: Two round trips across all nodes adds significant latency.
  - Not fault-tolerant by itself — needs additional protocols for recovery.

Vitess uses 2PC for cross-shard transactions (with metadata stored in a special "transaction manager" table to handle coordinator failures).

----- 10.2 PERCOLATOR MODEL -----
Google's Percolator (used conceptually in CockroachDB) extends MVCC-based transactions across nodes without a single coordinator bottleneck:

  - Transaction state (record) is stored in the data store itself, not on a separate coordinator.
  - "Write intents" (uncommitted writes) are stored alongside data.
  - Other transactions that encounter intents can check the transaction record to determine if the intent should be committed or aborted.
  - Allows recovery without blocking — any node can resolve stale intents.

CockroachDB's transaction model is heavily inspired by Percolator.

----- 10.3 SERIALIZABLE SNAPSHOT ISOLATION (SSI) -----

SSI is used by CockroachDB to detect and abort transactions that would violate serializability, without requiring pessimistic locking:

  - Every transaction reads from a consistent MVCC snapshot.
  - CockroachDB tracks read-write dependencies between concurrent transactions.
  - If a cycle in the dependency graph is detected (would violate serializability), one of the transactions is aborted and retried.
  - This allows high concurrency (no read locks) while guaranteeing serializability.

Client code should implement retry loops for transactions in CockroachDB.

11. FAULT TOLERANCE & HIGH AVAILABILITY
================================================================================
Distributed databases achieve fault tolerance through replication:

  REPLICATION FACTOR:
    - RF=3: Data on 3 nodes. Tolerate 1 node failure (quorum = 2).
    - RF=5: Data on 5 nodes. Tolerate 2 node failures (quorum = 3).
    - General rule: tolerate F failures with RF = 2F+1.

  AUTOMATIC FAILOVER:
    CockroachDB:
      - If a leaseholder node dies, Raft automatically elects a new leader from the remaining replicas.
      - Reads/writes resume in seconds (after election timeout).
      - No manual intervention needed.

    Vitess:
      - VTTablet monitors MySQL health via heartbeats.
      - On primary failure, Vitess (with Orchestrator or built-in durability policies) promotes a replica to primary.
      - VTGate is updated with new primary location via topology service.

  NODE RECOVERY:
    - When a failed node comes back online, it rejoins and catches up on missed writes via log replication (CockroachDB) or MySQL binlog (Vitess).
    - CockroachDB: The recovered node receives a Raft snapshot if too far behind.

  DATA CENTER FAILURE:
    - With nodes spread across 3+ data centers, losing one DC is survivable as long as quorum is maintained across remaining DCs.
    - CockroachDB allows specifying locality labels for replica placement (e.g., ensure each replica is in a different region/zone).


================================================================================
12. GEO-DISTRIBUTION & MULTI-REGION DEPLOYMENTS
================================================================================
Both CockroachDB and Vitess support globally distributed deployments.

  CockroachDB Multi-Region:
    - Locality labels: Each node is tagged with region/zone metadata.
    - Zone configs: Tell CockroachDB where to place replicas. Example: keep 2 replicas in us-east, 1 in eu-west.
    - Multi-region table types:
        * GLOBAL tables: All reads are local (replicated everywhere, eventual read).
        * REGIONAL BY TABLE: Leaseholder placed in the table's designated region.
        * REGIONAL BY ROW: Each row pinned to a specific region.
    - Follower reads: Read from a local replica (slightly stale, ~4.8s by default). Much lower latency for read-heavy, globally distributed workloads.
    - Beneficial for: apps where different users own different rows (e.g., European user data stays in Europe for compliance + low latency).

  Vitess Multi-Region:
    - Multiple keyspace instances deployed in different regions.
    - VReplication streams changes between regions.
    - Each region can serve reads locally; writes go to the primary region.
    - More complex to configure than CockroachDB's native multi-region support.

  Latency Considerations:
    - Speed of light: US-East ↔ EU-West ≈ 80–100ms round trip.
    - Raft consensus requires quorum acknowledgment → latency for writes is bounded by the slowest quorum member.
    - Geo-distributing replicas increases write latency unless the leaseholder is local to the write origin.
    - Design: Keep write-heavy workloads in a single region; use follower reads for global read scaling.

13. OPERATIONAL CONSIDERATIONS
================================================================================

  MONITORING:
    - CockroachDB: Exposes Prometheus metrics, built-in web console (DB Console) at port 8080. Key metrics: SQL QPS, p99 latency, range count leaseholder distribution, CPU per node.
    - Vitess: VTGate and VTTablet expose Prometheus metrics. Vitess also has a built-in web UI (vtctld web). Key metrics: query latency, shard balance, replication lag.

  SCHEMA CHANGES:
    - CockroachDB: Online DDL — ALTER TABLE does not lock the table. Uses a multi-stage schema change process that keeps the table available during the migration.
    - Vitess: Uses gh-ost (GitHub's Online Schema Change) or pt-online-schema- change. These tools create a shadow table, apply the change, and swap. Must be applied to all shards.

  BACKUP & RESTORE:
    - CockroachDB: `BACKUP` command exports to S3/GCS in a CockroachDB-native format. `RESTORE` imports it. Incremental backups supported.
    - Vitess: Uses mysqldump, xtrabackup, or mysqlpump per shard. Restoring requires restoring each shard independently.

  UPGRADES:
    - CockroachDB: Rolling upgrades — upgrade one node at a time. The cluster continues serving traffic during the upgrade.
    - Vitess: Upgrade VTGate and VTTablet independently (they're separate processes). MySQL upgrades follow standard MySQL rolling upgrade procedures.

  CONNECTION MANAGEMENT:
    - CockroachDB: Has a built-in connection pooler. For high connection counts, use PgBouncer in front of CockroachDB nodes.
    - Vitess: VTGate provides excellent connection pooling out of the box. It multiplexes many client connections into a small pool of MySQL connections, drastically reducing MySQL connection overhead.

14. WHEN TO USE DISTRIBUTED DATABASES (vs. ALTERNATIVES)
================================================================================
USE DISTRIBUTED DATABASES WHEN:
  ✔ Data volume exceeds what a single node can handle (>few TB actively queried).
  ✔ Write throughput exceeds single-node capability (>10K-100K writes/second).
  ✔ High availability (99.99%+) is required with no manual failover.
  ✔ Global user base requiring low-latency reads from multiple regions.
  ✔ Regulatory requirements to keep certain data in specific geographic regions.
  ✔ You need to scale out without rewriting your application's data access layer.

CONSIDER ALTERNATIVES FIRST:
  ✗ Your data fits comfortably on a single large machine (256GB RAM, 10TB SSD).
    → A well-tuned PostgreSQL or MySQL instance handles millions of queries/day.
  ✗ Read scaling is your only problem.
    → Add read replicas to existing single-node database.
  ✗ Your workload is mostly analytical (OLAP), not transactional (OLTP).
    → Use a columnar warehouse: BigQuery, Snowflake, ClickHouse, Redshift.
  ✗ Your consistency requirements are relaxed.
    → NoSQL databases (Cassandra, MongoDB) may be simpler to operate.
  ✗ You're in early stages with uncertain scale needs.
    → Start simple; distributed databases add significant operational complexity.

THE MIGRATION PATH (common pattern):
  1. Start with single-node PostgreSQL or MySQL.
  2. Add read replicas when read traffic grows.
  3. Introduce caching (Redis) for hot data.
  4. When writes saturate the primary → migrate to CockroachDB or Vitess.

For Vitess specifically, it is ideal when:
  - You already have a large MySQL investment and cannot switch databases.
  - You need to scale MySQL horizontally with minimal application changes.
  - Your team has MySQL expertise.

For CockroachDB specifically, it is ideal when:
  - You're building a new application (greenfield) that needs global scale.
  - You want strong ACID guarantees across distributed nodes without complexity.
  - You prefer PostgreSQL compatibility.
