 1. WHAT IS SSL / TLS?
================================================================================

SSL (Secure Sockets Layer) and TLS (Transport Layer Security) are cryptographic
protocols that provide:

  ✅ CONFIDENTIALITY  — Data is encrypted; no eavesdropper can read it
  ✅ INTEGRITY        — Data cannot be tampered in transit (MAC/HMAC)
  ✅ AUTHENTICATION   — You talk to who you think you're talking to (certs)
  ✅ NON-REPUDIATION  — The sender cannot deny sending (digital signatures)

In simple terms: TLS is the "S" in HTTPS.

LAYER in the OSI Model:
  ┌──────────────────────────────────────┐
  │  Application Layer  (HTTP, FTP, SMTP)│
  ├──────────────────────────────────────┤
  │  TLS / SSL Layer  ◄── sits here      │
  ├──────────────────────────────────────┤
  │  Transport Layer  (TCP)              │
  ├──────────────────────────────────────┤
  │  Network Layer   (IP)                │
  └──────────────────────────────────────┘

TLS operates between the Application and Transport layers.
It wraps the application data before handing it to TCP.

Common name confusion:
  • "SSL" is often used colloquially, but SSL is actually deprecated.
  • When people say "SSL certificate," they mean TLS certificate.
  • Modern systems use TLS 1.2 or TLS 1.3 exclusively.

 2. HISTORY & VERSION EVOLUTION
================================================================================

  Version        Year    Status          Key Notes
  ─────────────────────────────────────────────────────────────────────────────
  SSL 1.0        1994    Never released  Internal Netscape; had serious bugs
  SSL 2.0        1995    Deprecated      First public version; broken (POODLE,
                                          DROWN attacks)
  SSL 3.0        1996    Deprecated      Better, but vulnerable to POODLE attack
                                          (2014). RFC 7568 prohibits use.
  TLS 1.0        1999    Deprecated      Based on SSL 3.0; vulnerable to BEAST,
  (RFC 2246)             (2021)           POODLE-v2. PCI DSS banned it in 2018.
  TLS 1.1        2006    Deprecated      Fixed some BEAST; still weak.
  (RFC 4346)             (2021)           Browsers dropped it in 2020.
  TLS 1.2        2008    WIDELY USED     Introduced AEAD ciphers (GCM), SHA-256,
  (RFC 5246)             (current)        strong cipher suites. Still safe.
  TLS 1.3        2018    RECOMMENDED     Removed legacy cruft, 1-RTT handshake,
  (RFC 8446)             (modern)         0-RTT resumption, Forward Secrecy by
                                          default, removed RSA key exchange.

Why did SSL die?
  • SSL 3.0 → POODLE attack (Padding Oracle On Downgraded Legacy Encryption)
  • Weak cipher support (RC4, export-grade ciphers)
  • No Perfect Forward Secrecy
  • Lack of AEAD (Authenticated Encryption with Associated Data)

Key Insight for interviews:
  → TLS 1.3 removed all non-forward-secret key exchanges (no more static RSA).
  → All TLS 1.3 cipher suites are AEAD-based.
  → The term "SSL" survives only in marketing; technically it's always TLS now.

 3. CORE CRYPTOGRAPHY CONCEPTS (MUST KNOW)
================================================================================

─────────────────────────────────────────────────────────────────────────────
 3.1 SYMMETRIC ENCRYPTION
─────────────────────────────────────────────────────────────────────────────
  • Same key used for both encryption and decryption.
  • Very FAST — used for bulk data encryption.
  • Problem: How do you securely share the key? (Key Distribution Problem)

  Algorithms:
    AES-128-GCM  — 128-bit key, Galois/Counter Mode (AEAD) ✅ Modern
    AES-256-GCM  — 256-bit key, stronger ✅ Modern
    AES-128-CBC  — Older block cipher mode; vulnerable to padding oracle
    ChaCha20     — Stream cipher; fast on mobile/IoT (no AES hardware accel)
    3DES         — Legacy, deprecated (too slow, 112-bit effective security)
    RC4          — Broken, never use

  GCM (Galois/Counter Mode):
    • Provides both encryption AND integrity (AEAD)
    • No need for separate HMAC
    • Parallelizable — very fast

─────────────────────────────────────────────────────────────────────────────
 3.2 ASYMMETRIC ENCRYPTION (PUBLIC KEY CRYPTOGRAPHY)
─────────────────────────────────────────────────────────────────────────────
  • Two mathematically linked keys: PUBLIC KEY + PRIVATE KEY
  • What one encrypts, only the other can decrypt.
  • SLOW — used only for key exchange and digital signatures.

  Encrypt with PUBLIC key  → only PRIVATE key can decrypt (confidentiality)
  Sign with PRIVATE key    → anyone with PUBLIC key can verify (authentication)

  Algorithms:
    RSA-2048 / RSA-4096  — Old standard; used for key exchange & signatures
    ECDSA (P-256, P-384) — Elliptic Curve; smaller key, faster, same security
    ECDH / ECDHE         — Elliptic Curve Diffie-Hellman (for key exchange)
    Ed25519              — Modern EdDSA; fast, small, used in TLS 1.3

  Why ECDSA > RSA:
    • 256-bit ECDSA ≈ 3072-bit RSA in security
    • Shorter certificates = less bandwidth
    • Faster handshakes

─────────────────────────────────────────────────────────────────────────────
 3.3 KEY EXCHANGE (DIFFIE-HELLMAN)
─────────────────────────────────────────────────────────────────────────────
  The Diffie-Hellman (DH) protocol lets two parties agree on a shared secret
  over a public channel WITHOUT transmitting the secret.

  Classic DH (Finite Field):
    Alice and Bob agree on public values g (generator) and p (prime).
    Alice picks private a, sends g^a mod p
    Bob picks private b, sends g^b mod p
    Both compute: shared_secret = g^(ab) mod p

  ECDHE (Elliptic Curve Diffie-Hellman Ephemeral):
    • Same concept but uses elliptic curve math — much smaller keys.
    • "Ephemeral" = new key pair generated for EVERY session.
    • This gives PERFECT FORWARD SECRECY.

─────────────────────────────────────────────────────────────────────────────
 3.4 PERFECT FORWARD SECRECY (PFS)
─────────────────────────────────────────────────────────────────────────────
  Definition: If the server's long-term private key is compromised LATER,
              past encrypted sessions CANNOT be decrypted.

  How it works:
    • Each session uses EPHEMERAL (temporary) key pairs.
    • Session keys are discarded after the session ends.
    • Even if someone recorded all traffic + later stole the private key,
      they cannot decrypt old sessions because ephemeral keys are gone.

  PFS is achieved by: ECDHE or DHE key exchange
  PFS is NOT achieved by: Static RSA key exchange (deprecated in TLS 1.3)

  TLS 1.3: PFS is MANDATORY. All supported cipher suites use ECDHE.
  TLS 1.2: PFS is optional; depends on cipher suite chosen.

─────────────────────────────────────────────────────────────────────────────
 3.5 HASHING & MAC
─────────────────────────────────────────────────────────────────────────────
  Hash Functions: One-way; produce fixed-length digest. Used for integrity.
    MD5    — Broken (collisions). Never use for security.
    SHA-1  — Broken (collisions since 2017). Deprecated.
    SHA-256, SHA-384, SHA-512  — Secure (SHA-2 family) ✅

  HMAC (Hash-based Message Authentication Code):
    • Combines hash + secret key to verify both integrity AND authenticity.
    • HMAC-SHA256 used in TLS 1.2 (with CBC cipher suites).

  AEAD (Authenticated Encryption with Associated Data):
    • Modern replacement for MAC-then-Encrypt or Encrypt-then-MAC.
    • AES-GCM and ChaCha20-Poly1305 are AEAD.
    • Single algorithm handles both confidentiality AND integrity.

─────────────────────────────────────────────────────────────────────────────
 3.6 DIGITAL SIGNATURES
─────────────────────────────────────────────────────────────────────────────
  Purpose: Prove that a message was created by the holder of a private key.

  How:
    1. Hash the message → H
    2. Encrypt H with PRIVATE key → Signature
    3. Recipient decrypts Signature with PUBLIC key → H'
    4. Hash received message → H
    5. If H == H', signature is valid.

  Used in TLS for:
    • Certificate signing (CA signs server cert)
    • Server authentication during handshake
    • Client authentication (mTLS)

 4. PUBLIC KEY INFRASTRUCTURE (PKI)
================================================================================

PKI is the entire ecosystem of hardware, software, people, policies, and
procedures that manage digital certificates and public-key encryption.

Components:
  ┌─────────────────────────────────────────────────────────────────────────┐
  │                            TRUST HIERARCHY                              │
  │                                                                         │
  │   Root CA (self-signed)           ← Pre-installed in OS/browsers       │
  │       │                                                                 │
  │       ├── Intermediate CA 1       ← Signed by Root CA                  │
  │       │       │                                                         │
  │       │       ├── Intermediate CA 2  ← Signed by Intermediate CA 1    │
  │       │       │       │                                                 │
  │       │       │       └── End-Entity Cert (your server cert)           │
  │       │       │               ← Signed by Intermediate CA 2            │
  │       │       │                                                         │
  │       │       └── End-Entity Cert (another server)                     │
  │       │                                                                 │
  │       └── Intermediate CA 3                                             │
  └─────────────────────────────────────────────────────────────────────────┘

Roles:
  Root CA:          Ultimate trust anchor. Rarely used directly.
                    Private key kept OFFLINE (air-gapped hardware).
  Intermediate CA:  Intermediary; signs end-entity certs. Online.
                    If compromised, Root CA can revoke just this cert.
  End-Entity Cert:  The server certificate you install on nginx/Apache.
  Registration CA:  Handles identity verification before cert issuance.

Why intermediate CAs?
  • Protects Root CA private key (never online = never compromised easily)
  • Root CA can revoke an intermediate CA without replacing root trust
  • Allows organizational separation of certificate issuance

Major Certificate Authorities (CAs):
  • DigiCert, Comodo/Sectigo, GlobalSign, Let's Encrypt (free), Entrust
  • Browsers ship with ~150 pre-trusted Root CAs
  • Any one of them can issue a cert for any domain (historically problematic)

Certificate Transparency (CT):
  • All publicly trusted CAs must log every certificate to public CT logs.
  • Browsers check CT logs to detect mis-issued certificates.
  • Enables detection of unauthorized cert issuance for your domain.

 5. X.509 CERTIFICATES — DEEP DIVE
================================================================================

A certificate is a digitally signed document that binds a PUBLIC KEY to an
IDENTITY (domain, organization, or person).

X.509 Certificate Fields:
  ┌──────────────────────────────────────────────────────────────────────┐
  │ Field                  │ Example Value                               │
  ├──────────────────────────────────────────────────────────────────────┤
  │ Version                │ 3 (X.509 v3 is current standard)            │
  │ Serial Number          │ 0x1A2B3C... (unique per CA)                 │
  │ Signature Algorithm    │ sha256WithRSAEncryption / ecdsa-with-SHA256  │
  │ Issuer                 │ CN=DigiCert Global CA G2, O=DigiCert        │
  │ Validity - Not Before  │ 2024-01-01 00:00:00 UTC                     │
  │ Validity - Not After   │ 2025-01-01 23:59:59 UTC                     │
  │ Subject                │ CN=*.example.com, O=Example Corp, C=US      │
  │ Subject Public Key     │ RSA 2048-bit or EC P-256 public key         │
  │ Key Usage              │ Digital Signature, Key Encipherment          │
  │ Extended Key Usage     │ TLS Web Server Authentication               │
  │ Subject Alt Names      │ DNS:example.com, DNS:www.example.com        │
  │ CRL Distribution Point │ http://crl.digicert.com/...crl              │
  │ OCSP URL               │ http://ocsp.digicert.com                    │
  │ Certificate Policies   │ OID references for DV/OV/EV policies        │
  │ CA Issuers URL         │ URL to download intermediate cert           │
  │ Signature              │ CA's digital signature over all above        │
  └──────────────────────────────────────────────────────────────────────┘

Certificate Formats:
  .pem  — Base64 encoded (most common on Linux; ---BEGIN CERTIFICATE---)
  .der  — Binary DER encoding (Java loves this)
  .pfx/.p12 — PKCS#12; contains cert + private key + chain (Windows)
  .crt  — Often PEM but sometimes DER (ambiguous extension)
  .key  — Private key file

How to view a cert:
  openssl x509 -in cert.pem -text -noout
  openssl s_client -connect example.com:443 -showcerts

CSR (Certificate Signing Request):
  • You generate a private key + CSR on your server.
  • CSR contains your public key + identity info.
  • You submit CSR to CA → CA signs it → CA returns certificate.
  • Private key NEVER leaves your server.

  openssl req -new -newkey rsa:2048 -keyout server.key -out server.csr

 6. TLS HANDSHAKE — TLS 1.2 (STEP-BY-STEP)
================================================================================

TLS 1.2 Handshake takes 2 Round Trips (2-RTT) before data flows.

  Client                                                    Server
    │                                                          │
    │──── ClientHello ────────────────────────────────────────►│
    │     • TLS version supported (max: 1.2)                   │
    │     • Random bytes (client_random) 32 bytes              │
    │     • Session ID (for resumption)                        │
    │     • Cipher Suites supported (ordered by preference)    │
    │     • Compression methods (TLS 1.3 removes this)         │
    │     • Extensions (SNI, ALPN, supported_groups, etc.)     │
    │                                                          │
    │◄─── ServerHello ────────────────────────────────────────│
    │     • Chosen TLS version                                 │
    │     • Random bytes (server_random) 32 bytes              │
    │     • Chosen cipher suite                                │
    │     • Session ID                                         │
    │                                                          │
    │◄─── Certificate ────────────────────────────────────────│
    │     • Server's X.509 certificate (+ chain)               │
    │                                                          │
    │◄─── ServerKeyExchange (if DHE/ECDHE) ──────────────────│
    │     • Server's ephemeral DH/ECDH public key              │
    │     • Signed with server's private key (from cert)       │
    │     (Not sent for RSA key exchange)                      │
    │                                                          │
    │◄─── CertificateRequest (optional — for mTLS) ───────────│
    │◄─── ServerHelloDone ────────────────────────────────────│
    │                                                          │
    │  [Client validates server certificate]                   │
    │  [Client extracts server's public key]                   │
    │  [Client generates pre_master_secret]                    │
    │  [Client computes master_secret from:                    │
    │     PRF(pre_master_secret, "master secret",              │
    │         client_random + server_random)]                  │
    │                                                          │
    │──── ClientKeyExchange ──────────────────────────────────►│
    │     • Client's ECDH public key (if ECDHE)                │
    │     • Or: pre_master_secret encrypted with server's      │
    │       RSA public key (if RSA key exchange — old method)  │
    │                                                          │
    │──── Certificate (optional — for mTLS) ─────────────────►│
    │──── CertificateVerify (optional — for mTLS) ───────────►│
    │     • Signature over handshake transcript                │
    │                                                          │
    │──── ChangeCipherSpec ───────────────────────────────────►│
    │     • Signal: switching to encrypted communication       │
    │──── Finished (encrypted) ───────────────────────────────►│
    │     • Hash of entire handshake transcript                │
    │                                                          │
    │◄─── ChangeCipherSpec ───────────────────────────────────│
    │◄─── Finished (encrypted) ───────────────────────────────│
    │     • Hash of entire handshake transcript                │
    │                                                          │
    │  ══════════ Encrypted Application Data Flows ══════════  │
    │                                                          │

Key Derivation in TLS 1.2:
  pre_master_secret → (via PRF with both randoms) → master_secret
  master_secret     → (key material expansion)    → 
    client_write_key, server_write_key,
    client_write_MAC, server_write_MAC,
    client_write_IV,  server_write_IV

PRF = Pseudo-Random Function (HMAC-based in TLS 1.2)

Vulnerabilities of TLS 1.2 Handshake:
  • RSA key exchange has no PFS (static RSA — deprecated but was allowed)
  • Multiple negotiation steps = more attack surface (downgrade attacks)
  • ChangeCipherSpec injection was a known attack vector
  • 2-RTT adds latency (matters for mobile/high-latency networks)

 7. TLS HANDSHAKE — TLS 1.3 (IMPROVEMENTS)
================================================================================

TLS 1.3 Handshake — 1-RTT (half the latency of TLS 1.2)

  Client                                                    Server
    │                                                          │
    │──── ClientHello ────────────────────────────────────────►│
    │     • Supported versions: [TLS 1.3]                      │
    │     • Random (32 bytes)                                  │
    │     • Session ticket (for 0-RTT if resuming)             │
    │     • Supported cipher suites                            │
    │     • key_share: Client's ECDHE public key               │
    │       (CLIENT GUESSES which group server will pick —     │
    │        sends key share preemptively!)                    │
    │     • supported_groups (ECDHE curves supported)          │
    │     • Extensions: SNI, ALPN, psk_key_exchange_modes      │
    │                                                          │
    │◄─── ServerHello ────────────────────────────────────────│
    │     • Chosen version: TLS 1.3                            │
    │     • Random                                             │
    │     • key_share: Server's ECDHE public key               │
    │     • Chosen cipher suite                                │
    │                                                          │
    │  [Both now compute shared_secret via ECDHE]             │
    │  [TLS 1.3 uses HKDF for key derivation — not PRF]       │
    │                                                          │
    │◄─── {EncryptedExtensions} ──────────────────────────────│  ← encrypted!
    │◄─── {CertificateRequest}  (optional mTLS) ─────────────│
    │◄─── {Certificate} ──────────────────────────────────────│  ← encrypted!
    │◄─── {CertificateVerify} ────────────────────────────────│  ← encrypted!
    │◄─── {Finished} ─────────────────────────────────────────│  ← encrypted!
    │                                                          │
    │  [Client verifies server cert + Finished MAC]            │
    │                                                          │
    │──── {Certificate} (if mTLS) ───────────────────────────►│
    │──── {CertificateVerify} (if mTLS) ─────────────────────►│
    │──── {Finished} ────────────────────────────────────────►│
    │                                                          │
    │  ══════════ Encrypted Application Data Flows ══════════  │
    │                                                          │

0-RTT (Zero Round Trip Time) Resumption in TLS 1.3:
  • Client sends application data ALONGSIDE the first ClientHello
  • Uses a Pre-Shared Key (PSK) from a previous session
  • Risk: Replay attacks (0-RTT data can be replayed by an attacker)
  • Should only be used for idempotent requests (GET, not POST)
  • Server must implement anti-replay mechanisms

TLS 1.3 Key Derivation — HKDF:
  Uses HMAC-based Extract-and-Expand Key Derivation Function.
  Produces separate keys for: handshake, application data, each direction.
  More deterministic and analyzable than TLS 1.2's PRF.

WHAT TLS 1.3 REMOVED (compared to 1.2):
  ✗ RSA key exchange (no PFS)
  ✗ Static DH key exchange
  ✗ RC4, DES, 3DES, EXPORT ciphers
  ✗ MD5, SHA-1 in handshake signatures
  ✗ CBC mode cipher suites
  ✗ Compression (CRIME attack)
  ✗ Renegotiation
  ✗ ChangeCipherSpec message (now implicit)
  ✗ ServerKeyExchange (merged into ClientHello/ServerHello key_share)

 8. TLS 1.2 vs TLS 1.3 — SIDE-BY-SIDE COMPARISON
================================================================================

  Feature                    TLS 1.2              TLS 1.3
  ─────────────────────────────────────────────────────────────────────────────
  Handshake RTTs             2-RTT                1-RTT
  0-RTT Resumption           No                   Yes (with replay risk)
  Key Exchange               RSA / DHE / ECDHE    ECDHE only (mandatory)
  Perfect Forward Secrecy    Optional             Mandatory
  Cipher Suite Options       Many (incl. weak)    5 (all AEAD, all strong)
  Encryption of Certs        No (visible)         Yes (encrypted after Hello)
  HMAC Algorithm             MD5 possible, SHA-1  Only SHA-256, SHA-384
  Compression Support        Yes (CRIME attack)   No
  Renegotiation              Yes (attack surface) No
  Downgrade Protection       Weak (POODLE risk)   Strong (version signaling)
  ChangeCipherSpec           Explicit message     Implicit
  Key Derivation             PRF (HMAC-based)     HKDF
  Standardized               2008                 2018 (RFC 8446)
  Privacy of Server Cert     Not encrypted        Encrypted (ECH in progress)

Cipher Suites in TLS 1.3 (only 5 allowed):
  • TLS_AES_128_GCM_SHA256
  • TLS_AES_256_GCM_SHA384
  • TLS_CHACHA20_POLY1305_SHA256
  • TLS_AES_128_CCM_SHA256
  • TLS_AES_128_CCM_8_SHA256

 9. CIPHER SUITES — HOW TO READ THEM
================================================================================

Format (TLS 1.2):
  TLS_[KEY_EXCHANGE]_[AUTHENTICATION]_WITH_[CIPHER]_[MODE]_[MAC]

Example:
  TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
   │     │     │         │    │   │    │
   │     │     │         │    │   │    └── MAC: SHA256
   │     │     │         │    │   └─────── Mode: GCM (AEAD — no separate MAC)
   │     │     │         │    └─────────── Key size: 128-bit
   │     │     │         └──────────────── Cipher: AES
   │     │     └────────────────────────── Auth: RSA cert validates ECDHE
   │     └──────────────────────────────── Key Exchange: ECDHE (PFS)
   └────────────────────────────────────── Protocol: TLS

More examples:
  TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384   ← Strong (ECDSA cert)
  TLS_ECDHE_RSA_WITH_CHACHA20_POLY1305_SHA256 ← Mobile-friendly
  TLS_RSA_WITH_AES_128_CBC_SHA              ← Weak (no PFS, CBC, SHA1)
  TLS_RSA_WITH_RC4_128_MD5                  ← Broken — never use

How to check a server's supported ciphers:
  nmap --script ssl-enum-ciphers -p 443 example.com
  sslyze --regular example.com
  curl https://www.ssllabs.com/ssltest/ (online tool)

Good cipher suite config (nginx):
  ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:
              ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:
              ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;
  ssl_prefer_server_ciphers off;  ← Let client choose in TLS 1.3

 10. CERTIFICATE TYPES
================================================================================

─────────────────────────────────────────────────────────────────────────────
 BY VALIDATION LEVEL
─────────────────────────────────────────────────────────────────────────────

 DV (Domain Validation):
   • CA only verifies domain ownership (DNS record or file on server).
   • Issued in minutes. Free (Let's Encrypt).
   • Shows padlock. No organization info.
   • Good for: blogs, personal sites, APIs.
   • NOT for: e-commerce, banking.

 OV (Organization Validation):
   • CA verifies domain + organization exists + is legitimate.
   • Takes days. Shows org name in cert details.
   • Good for: business websites, SaaS.

 EV (Extended Validation):
   • Strictest. CA verifies legal identity, physical location, phone.
   • Takes weeks. Previously showed green bar in browsers.
   • Modern browsers removed the green bar (user rarely notices).
   • Good for: banks, governments, high-trust applications.

─────────────────────────────────────────────────────────────────────────────
 BY COVERAGE SCOPE
─────────────────────────────────────────────────────────────────────────────

 Single Domain:
   CN=www.example.com — covers only www.example.com

 Wildcard Certificate:
   CN=*.example.com
   • Covers: www.example.com, api.example.com, mail.example.com
   • Does NOT cover: sub.api.example.com (only one level)
   • Does NOT cover: example.com itself (need SAN or separate cert)

 Multi-Domain / SAN (Subject Alternative Name):
   SAN: DNS:example.com, DNS:www.example.com, DNS:api.example.com,
        DNS:shop.example.com, IP:192.168.1.1
   • Can cover completely different domains in ONE cert.
   • Modern standard — CN field is now ignored for matching by browsers.

─────────────────────────────────────────────────────────────────────────────
 SPECIAL TYPES
─────────────────────────────────────────────────────────────────────────────

 Self-Signed Certificate:
   • Signed with its own private key (no CA involvement).
   • Browsers show "Not Secure" warning.
   • OK for internal use, development, internal microservices.
   • NOT trusted by public browsers.

 Code Signing Certificate:
   • Signs software binaries (not websites).
   • OS shows publisher identity when installing software.

 Client Certificate:
   • Used to authenticate CLIENT to server (mTLS).
   • Can identify a person, device, or microservice.

 11. CHAIN OF TRUST & CERTIFICATE VALIDATION
================================================================================

Certificate Path Validation (what your browser does):

  Step 1: CHAIN BUILDING
    Browser receives server cert + any intermediate certs.
    Builds the chain:
      server cert → intermediate CA → root CA
    Root CA must be in browser's/OS's trust store.

  Step 2: SIGNATURE VERIFICATION
    For each cert in chain:
      Verify the signature using the ISSUER's public key.
      (Intermediate's signature verified by Root's public key)
      (Server cert's signature verified by Intermediate's public key)

  Step 3: VALIDITY PERIOD
    Check current date is between NotBefore and NotAfter.
    (Common mistake: forgetting to auto-renew certs!)

  Step 4: REVOCATION CHECK
    Check if cert has been revoked via CRL or OCSP.

  Step 5: NAME VALIDATION
    Check that the server hostname matches CN or SAN in the cert.
    *.example.com matches api.example.com? Yes.
    *.example.com matches api.v2.example.com? No.

  Step 6: KEY USAGE / EXTENDED KEY USAGE
    Verify cert is allowed to be used for TLS server auth.

  Step 7: CERTIFICATE TRANSPARENCY
    Check that the cert appears in CT logs (SCTs).
    Chrome requires 2+ SCTs for publicly trusted certs.

Trust Store:
  • OS-level: /etc/ssl/certs (Linux), Keychain (macOS), Registry (Windows)
  • Browser-level: Firefox has its own trust store (Mozilla Root Program)
  • Java: $JAVA_HOME/lib/security/cacerts (use keytool to manage)

Intermediate CA "Bundle" problem:
  Servers MUST send the full chain (server cert + all intermediates).
  If server only sends leaf cert, mobile clients or strict validators fail.
  Root cert should NOT be sent (client has it already).

 12. MUTUAL TLS (mTLS) — DEEP DIVE
================================================================================

In standard TLS:   Server proves identity to Client
In mutual TLS:     BOTH sides prove identity to each other

mTLS Flow (additions to standard handshake):
  • Server sends CertificateRequest during handshake
  • Client must send its own certificate
  • Client signs a CertificateVerify message with its private key
  • Server validates client cert against trusted CA

Use Cases:
  ✅ Microservice-to-microservice authentication (zero trust)
  ✅ API client authentication (instead of API keys)
  ✅ IoT device authentication (device has embedded cert)
  ✅ VPN clients
  ✅ B2B integrations where both parties need strong auth
  ✅ Banking and fintech (regulatory requirement)

Advantages over token/API key auth:
  • Cryptographically strong — cert cannot be guessed or brute-forced
  • Cert can be revoked immediately if compromised
  • Identity embedded in connection layer, not application layer
  • Works at TCP level — no application-level auth code needed

Practical Implementation:
  Nginx mTLS config:
    ssl_client_certificate /etc/nginx/client-ca.crt;
    ssl_verify_client on;
    ssl_verify_depth 2;

  Spring Boot (server-side):
    server.ssl.trust-store=classpath:truststore.jks
    server.ssl.trust-store-password=changeit
    server.ssl.client-auth=need  # or 'want' for optional

  Generating client cert:
    openssl genrsa -out client.key 2048
    openssl req -new -key client.key -out client.csr
    openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key
            -CAcreateserial -out client.crt -days 365

Service Mesh mTLS (Istio / Linkerd):
  • Automatically issues, rotates, and manages certs for every service
  • mTLS happens transparently — no application code changes
  • Envoy sidecar proxy handles the TLS termination
  • SPIFFE/SPIRE standard for workload identity certificates

Challenges:
  • Certificate lifecycle management (rotation, renewal)
  • Distributing CAs/certs to all services
  • Debugging — harder to troubleshoot than token auth
  • Overhead of managing PKI for internal services


================================================================================
 13. HTTPS — HOW IT BUILDS ON TLS
================================================================================

HTTPS = HTTP + TLS

Port: 443 (HTTP is port 80)

What HTTPS provides:
  • Encrypts HTTP request/response body AND headers
  • Hides URL path (the domain is visible via SNI, but path is encrypted)
  • Protects cookies, form data, session tokens, API keys
  • Server identity verification

What HTTPS does NOT hide:
  • The domain name (visible in SNI extension + DNS query)
  • IP addresses of client and server
  • Amount of data transferred (size patterns)
  • Timing of requests

HTTP → HTTPS Redirect:
  Server returns 301 Moved Permanently to https://
  Problem: First request is unencrypted → HSTS solves this

ALPN (Application Layer Protocol Negotiation):
  TLS extension that lets client/server negotiate HTTP version.
  Client sends: [h2, http/1.1] in ClientHello extensions.
  Server responds: chosen protocol (e.g., h2 for HTTP/2).
  This avoids an extra round trip to negotiate HTTP/2.

HTTP/2 and HTTP/3:
  HTTP/2 practically requires TLS (browsers enforce it).
  HTTP/3 uses QUIC (built on UDP), which has TLS 1.3 BUILT-IN.
  QUIC handshake is even faster — 0-RTT for known servers.


================================================================================
 14. SNI (SERVER NAME INDICATION)
================================================================================

Problem SNI Solves:
  One server, one IP address, MULTIPLE domains (virtual hosting).
  Without SNI, the server can't know WHICH certificate to present
  before the TLS handshake completes (it doesn't know the domain yet).

How SNI Works:
  Client sends the target hostname in the ClientHello message
  (BEFORE the TLS handshake is secured).
  Server uses SNI value to select the correct certificate.

  ClientHello → Extension: server_name = "api.example.com"
  Server sees "api.example.com" → picks api.example.com cert

Privacy Issue:
  SNI is sent in PLAINTEXT — ISPs, network admins can see it.
  This reveals which site you're visiting even with HTTPS.

ECH (Encrypted Client Hello) — TLS 1.3 Evolution:
  IETF draft (not yet widely deployed as of 2024).
  Encrypts the entire ClientHello using a public key from DNS (HTTPS record).
  Hides SNI and all other extensions from network observers.
  Will be a significant privacy improvement.

nginx SNI config:
  server {
      listen 443 ssl;
      server_name api.example.com;
      ssl_certificate /etc/nginx/certs/api.example.com.pem;
      ssl_certificate_key /etc/nginx/certs/api.example.com.key;
  }
  server {
      listen 443 ssl;
      server_name shop.example.com;
      ssl_certificate /etc/nginx/certs/shop.example.com.pem;
      ssl_certificate_key /etc/nginx/certs/shop.example.com.key;
  }


================================================================================
 15. HSTS (HTTP STRICT TRANSPORT SECURITY)
================================================================================

Purpose: Force browsers to ALWAYS use HTTPS for a domain.
Prevents SSL stripping attacks.

HTTP Header:
  Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

  max-age=31536000  → Remember this rule for 1 year (in seconds)
  includeSubDomains → Apply to all subdomains too
  preload           → Submit to browser preload list (hardcoded in browsers)

How it works:
  1. First visit: Browser connects over HTTPS (or gets redirected from HTTP).
  2. Server responds with HSTS header.
  3. Browser stores: "For domain example.com, ONLY use HTTPS for 1 year."
  4. All future requests: Browser automatically upgrades to HTTPS internally.
     Even if user types http:// or follows an http:// link.

SSL Stripping Attack (HSTS protects against this):
  Attacker between client and server downgrades HTTPS → HTTP.
  Client thinks it's on HTTP, so no encryption.
  With HSTS: browser refuses to connect over HTTP at all.

HSTS Preload List:
  List of domains hardcoded in Chrome, Firefox, Safari, Edge.
  Browser ALWAYS uses HTTPS for these domains — even on first ever visit.
  Submit at: https://hstspreload.org
  Warning: Very hard to UNDO. Only add when you're 100% committed to HTTPS.

Best Practice:
  • Set max-age to at least 1 year (31536000)
  • Include subdomains if you're sure all subdomains have HTTPS
  • Apply preload only after thorough testing


================================================================================
 16. TLS TERMINATION & OFFLOADING
================================================================================

TLS Termination = the point where encrypted TLS traffic is decrypted.

─────────────────────────────────────────────────────────────────────────────
 TERMINATION AT LOAD BALANCER / REVERSE PROXY
─────────────────────────────────────────────────────────────────────────────

  Internet → [HTTPS] → Load Balancer/Nginx → [HTTP] → Backend Servers

  Pros:
    • Centralized cert management (one place to update certs)
    • Backend servers freed from crypto overhead
    • Load balancer can inspect, route, modify HTTP traffic
    • Simpler backend configuration

  Cons:
    • Traffic from LB to backend is unencrypted (internal network risk)
    • Need to trust internal network OR use additional controls

  Common tools: nginx, HAProxy, AWS ALB/NLB, Cloudflare, Envoy

─────────────────────────────────────────────────────────────────────────────
 TLS PASSTHROUGH
─────────────────────────────────────────────────────────────────────────────

  Internet → [HTTPS] → Load Balancer → [HTTPS] → Backend Servers
                       (just routes, doesn't decrypt)

  Pros:
    • End-to-end encryption; LB cannot see traffic
    • Backend handles cert; mTLS can go all the way

  Cons:
    • LB can't do layer-7 routing (can only route by IP/port)
    • Each backend must manage its own certs
    • LB can't compress, cache, or inspect content

  Use case: mTLS requirement, compliance, or zero trust architectures

─────────────────────────────────────────────────────────────────────────────
 RE-ENCRYPTION (TLS RE-ORIGINATION)
─────────────────────────────────────────────────────────────────────────────

  Internet → [HTTPS] → LB (terminates + re-encrypts) → [HTTPS] → Backend

  Pros:
    • Encrypted all the way (end-to-end)
    • LB can still inspect traffic (it terminates and re-encrypts)

  Cons:
    • Double TLS overhead
    • LB needs to trust internal CA for backend certs
    • More complex cert management

─────────────────────────────────────────────────────────────────────────────
 HARDWARE SECURITY MODULES (HSM)
─────────────────────────────────────────────────────────────────────────────
  Physical devices that store private keys and perform crypto operations.
  Private key never leaves the HSM.
  Used in high-security environments (banks, governments, CAs).
  Cloud equivalents: AWS CloudHSM, Azure Dedicated HSM, GCP Cloud HSM.

Forwarded Headers (when LB terminates TLS):
  LB adds headers so backend knows original protocol:
    X-Forwarded-Proto: https
    X-Forwarded-For: 203.0.113.45
  Backend reads these to know client used HTTPS even though it got HTTP.

 17. CERTIFICATE PINNING
================================================================================

Problem: What if a rogue CA issues a valid cert for your domain?
  (This has happened: DigiNotar breach 2011, Comodo breach 2011)

Certificate Pinning:
  Client hard-codes which certificate (or public key) it will accept.
  Even if an attacker has a CA-signed cert, it won't match the pin.

Types:

  Certificate Pinning:
    Pin the exact certificate. Very strict.
    Problem: Must update app every cert renewal.

  Public Key Pinning (HPKP / Recommended approach):
    Pin the public key hash (SPKI hash).
    Public key stays the same across cert renewals.
    Only change when you rotate your key pair.

  CA Pinning:
    Pin the CA that issued your cert. Less strict but easier to manage.

  Intermediate CA Pinning:
    Pin a specific intermediate CA.

Mobile Implementation:
  Android (OkHttp):
    OkHttpClient client = new OkHttpClient.Builder()
        .certificatePinner(
            new CertificatePinner.Builder()
                .add("api.example.com",
                     "sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=")
                .build()
        ).build();

  iOS (URLSession):
    Implement URLSessionDelegate and validate server cert in
    didReceive challenge method.

HPKP (HTTP Public Key Pinning) — HTTP Header:
  Public-Key-Pins: pin-sha256="base64=="; max-age=5184000; includeSubDomains
  STATUS: Deprecated by browsers (too risky — misconfiguration = lockout)
          Chrome removed in 2018; Firefox in 2020.
  Replaced by: Certificate Transparency (CT) as safer alternative.

Risks of Certificate Pinning:
  • Pin wrong cert → app is broken for ALL users
  • Cert expires, pin not updated → app is broken
  • Hard to update in native apps (store review process)
  • Makes debugging harder (can't use Charles/Burp proxy)

Best Practice:
  • Pin 2+ keys: active key + backup key
  • Keep old pins valid for overlap during rotation
  • Have emergency plan to un-pin (server-side flag)

 18. SESSION RESUMPTION
================================================================================

Full TLS handshake is expensive (CPU + RTT). Session resumption avoids it.

─────────────────────────────────────────────────────────────────────────────
 SESSION ID (TLS 1.2)
─────────────────────────────────────────────────────────────────────────────
  • Server stores session parameters in memory, assigns Session ID.
  • Client includes Session ID in future ClientHello.
  • Server looks up the session, skips most of the handshake.
  • Resumes with cached master_secret.

  Problem:
    • Server must maintain state for all sessions (memory pressure).
    • Doesn't work with multiple server instances (ID from Server A
      not found on Server B).

─────────────────────────────────────────────────────────────────────────────
 SESSION TICKETS (TLS 1.2 Extension)
─────────────────────────────────────────────────────────────────────────────
  • Server encrypts session state into a ticket, sends to client.
  • Client presents ticket on next connection.
  • Server decrypts ticket → recovers session state. No server storage.
  • Works across multiple servers if they share the SAME ticket key.

  Problem:
    • All servers sharing ticket key means compromise of key = all sessions.
    • Undermines PFS if ticket keys are static (keys must be rotated).
    • Ticket key rotation requires coordination.

─────────────────────────────────────────────────────────────────────────────
 PSK (PRE-SHARED KEY) RESUMPTION — TLS 1.3
─────────────────────────────────────────────────────────────────────────────
  • TLS 1.3 replaces Session ID + Session Tickets with PSK (Pre-Shared Key).
  • After a session, server sends a NewSessionTicket message.
  • This ticket can be used as PSK in the next ClientHello.
  • 1-RTT resumption or 0-RTT (with replay risk).

  PFS in resumption:
    TLS 1.3 allows (EC)DHE + PSK together — gives forward secrecy even
    on resumed sessions.

 19. OCSP & CERTIFICATE REVOCATION
================================================================================

Why Revocation?
  If a private key is compromised → cert must be declared invalid BEFORE expiry.
  Without revocation, attackers can impersonate the server until cert expires.

─────────────────────────────────────────────────────────────────────────────
 CRL (Certificate Revocation List)
─────────────────────────────────────────────────────────────────────────────
  • CA publishes a list of all revoked serial numbers.
  • Client downloads CRL and checks if cert's serial is on it.
  • Problems:
    → CRL files get huge over time (millions of revoked certs).
    → CRLs are updated infrequently (24h delay possible).
    → Clients rarely check CRLs properly.

─────────────────────────────────────────────────────────────────────────────
 OCSP (Online Certificate Status Protocol)
─────────────────────────────────────────────────────────────────────────────
  • Client queries OCSP Responder (real-time) for cert status.
  • Responder returns: Good, Revoked, or Unknown.
  • Problem:
    → Privacy leak: OCSP responder knows which sites you visit.
    → Adds latency: extra network request per handshake.
    → Soft-fail: if OCSP unreachable, browsers often accept cert anyway.

─────────────────────────────────────────────────────────────────────────────
 OCSP STAPLING (Best Current Practice)
─────────────────────────────────────────────────────────────────────────────
  • SERVER queries OCSP responder periodically (every few hours).
  • Server caches the signed OCSP response.
  • During TLS handshake, server "staples" (includes) OCSP response.
  • Client gets cert + fresh revocation status in ONE step.

  Benefits:
    ✅ No privacy leak (client doesn't contact OCSP responder)
    ✅ No extra RTT for client
    ✅ Signed by CA → client can verify authenticity

  nginx config:
    ssl_stapling on;
    ssl_stapling_verify on;
    ssl_trusted_certificate /etc/nginx/chain.pem;
    resolver 8.8.8.8 valid=300s;

─────────────────────────────────────────────────────────────────────────────
 HARD FAIL vs SOFT FAIL
─────────────────────────────────────────────────────────────────────────────
  Hard Fail: If revocation status unknown → reject connection.
             More secure. Can break sites if OCSP responder is down.
  Soft Fail: If revocation status unknown → accept anyway.
             More available. Attackers can block OCSP (bypass revocation).

Modern Reality:
  Most browsers implement soft-fail.
  Let's Encrypt certs: 90-day validity. Short enough that revocation
  is less critical — just let them expire. This is the "short-lived cert" model.

 20. COMMON TLS ATTACKS & MITIGATIONS
================================================================================

─────────────────────────────────────────────────────────────────────────────
 POODLE (Padding Oracle On Downgraded Legacy Encryption) — 2014
─────────────────────────────────────────────────────────────────────────────
  Target: SSL 3.0 CBC mode
  Attack: Exploit padding validation in CBC mode to decrypt data.
  Requires: Ability to perform a downgrade attack to SSL 3.0.
  Mitigation: Disable SSL 3.0. Disable CBC cipher suites.
              Use TLS_FALLBACK_SCSV to prevent downgrade.

─────────────────────────────────────────────────────────────────────────────
 BEAST (Browser Exploit Against SSL/TLS) — 2011
─────────────────────────────────────────────────────────────────────────────
  Target: TLS 1.0 CBC mode
  Attack: Predict CBC initialization vectors to decrypt data.
  Mitigation: Use TLS 1.2+. Use RC4 was a temporary workaround (RC4 is broken).
              Modern fix: Use AEAD cipher suites (AES-GCM).

─────────────────────────────────────────────────────────────────────────────
 CRIME / BREACH — 2012/2013
─────────────────────────────────────────────────────────────────────────────
  CRIME: Exploits TLS-level compression to leak session tokens.
  BREACH: Exploits HTTP-level compression (gzip) to leak tokens.
  Mitigation:
    CRIME: TLS 1.3 removed TLS compression entirely.
    BREACH: Disable gzip for sensitive responses, add CSRF tokens,
            randomize compressed content.

─────────────────────────────────────────────────────────────────────────────
 HEARTBLEED — 2014
─────────────────────────────────────────────────────────────────────────────
  Target: OpenSSL 1.0.1 - 1.0.1f
  Attack: Bug in TLS Heartbeat extension. Attacker sends malformed
          heartbeat request → server reads beyond buffer boundary.
          Exposes up to 64KB of server memory per request.
          Could expose: private keys, session tokens, passwords.
  Severity: CVSS 10.0 (Critical). Affected millions of servers.
  Mitigation: Patch OpenSSL. Rotate private keys and certs.
              Revoke and reissue all certs.

─────────────────────────────────────────────────────────────────────────────
 DROWN — 2016
─────────────────────────────────────────────────────────────────────────────
  Target: Servers that support SSLv2 (even for other services)
  Attack: If a server's RSA key is used anywhere with SSLv2, attacker
          can use SSLv2 weakness to decrypt TLS sessions using same key.
  Mitigation: Disable SSLv2 on ALL services using the same key pair.

─────────────────────────────────────────────────────────────────────────────
 DOWNGRADE ATTACKS (FREAK, Logjam)
─────────────────────────────────────────────────────────────────────────────
  FREAK (2015): Force RSA_EXPORT (512-bit RSA) downgrade.
  Logjam (2015): Force DHE_EXPORT (512-bit DH) downgrade.
  Mitigation:
    • Remove export-grade cipher suites.
    • Use TLS_FALLBACK_SCSV (RFC 7507) to signal intentional downgrade.
    • Use DHE with 2048-bit groups minimum (Logjam targets 1024-bit).

─────────────────────────────────────────────────────────────────────────────
 MAN-IN-THE-MIDDLE (MITM)
─────────────────────────────────────────────────────────────────────────────
  Attacker intercepts traffic and presents its own cert.
  Possible if:
    • Client ignores cert warnings (user error).
    • Attacker has their own CA in client's trust store (corporate proxies).
    • Rogue CA issues cert for victim's domain.
    • DNS is hijacked (attacker redirects to their server).
  Mitigation:
    • HSTS + preloading
    • Certificate Transparency
    • Certificate Pinning (for mobile apps)
    • DNSSEC (to prevent DNS hijacking)
    • Strict cert validation (no soft-fail)

─────────────────────────────────────────────────────────────────────────────
 LUCKY THIRTEEN — 2013
─────────────────────────────────────────────────────────────────────────────
  Target: TLS CBC mode
  Attack: Timing side-channel attack on MAC-then-Encrypt. Attacker
          measures time differences in server responses to determine
          plaintext bytes.
  Mitigation: AEAD cipher suites (AES-GCM). TLS 1.3 removes CBC.

─────────────────────────────────────────────────────────────────────────────
 SWEET32 — 2016
─────────────────────────────────────────────────────────────────────────────
  Target: 64-bit block ciphers (3DES, Blowfish)
  Attack: Birthday attack on small block size. After ~2^32 blocks,
          collision in block cipher allows plaintext recovery.
  Mitigation: Disable 3DES and 64-bit block ciphers. Use AES (128-bit blocks).

─────────────────────────────────────────────────────────────────────────────
 RENEGOTIATION ATTACK — 2009
─────────────────────────────────────────────────────────────────────────────
  TLS 1.2 allowed renegotiation (changing cipher suite mid-session).
  Attack: Inject data into renegotiated session.
  Mitigation: RFC 5746 "Renegotiation Indication Extension" — binds
              renegotiation to current session. TLS 1.3 removed renegotiation.

 21. TLS IN MICROSERVICES / DISTRIBUTED SYSTEMS
================================================================================

─────────────────────────────────────────────────────────────────────────────
 ZERO TRUST NETWORKING
─────────────────────────────────────────────────────────────────────────────
  Principle: "Never trust, always verify."
  Even internal network traffic should be encrypted and authenticated.
  mTLS is the foundation of zero-trust between services.

─────────────────────────────────────────────────────────────────────────────
 SERVICE MESH (Istio, Linkerd, Consul Connect)
─────────────────────────────────────────────────────────────────────────────
  • Every service gets a sidecar proxy (Envoy).
  • Sidecar handles TLS transparently (app code unchanged).
  • Istio CA (Citadel) issues short-lived SPIFFE certs to each workload.
  • Automatic cert rotation every 24h.
  • Traffic policies enforced at sidecar level.

  SPIFFE (Secure Production Identity Framework for Everyone):
    Standard for workload identity in distributed systems.
    Each workload gets a SPIFFE Verifiable Identity Document (SVID).
    Format: spiffe://trust-domain/path (e.g., spiffe://example.com/frontend)
    Encoded in X.509 cert's SAN field.

─────────────────────────────────────────────────────────────────────────────
 CERT MANAGEMENT AT SCALE
─────────────────────────────────────────────────────────────────────────────
  Tools:
    cert-manager (Kubernetes): Auto-issue and rotate certs using Let's Encrypt
                               or internal CA.
    Vault (HashiCorp): PKI secrets engine; issues dynamic short-lived certs.
    AWS ACM: Manages TLS certs for AWS services (ALB, CloudFront).
    Let's Encrypt + ACME: Automated cert issuance and renewal.

  cert-manager example:
    apiVersion: cert-manager.io/v1
    kind: Certificate
    metadata:
      name: api-tls
    spec:
      secretName: api-tls-secret
      issuerRef:
        name: letsencrypt-prod
        kind: ClusterIssuer
      dnsNames:
        - api.example.com

─────────────────────────────────────────────────────────────────────────────
 TLS PERFORMANCE IN MICROSERVICES
─────────────────────────────────────────────────────────────────────────────
  TLS Overhead (modern hardware):
    • TLS 1.3 handshake: ~1ms additional latency (AES-NI hardware)
    • Throughput overhead: ~1-3% CPU for AES-GCM (hardware accelerated)
    • Without hardware AES: ~10-15% overhead

  Optimizations:
    • TLS 1.3 0-RTT for reconnecting clients
    • AES-NI (AES hardware acceleration — available on all modern servers)
    • ECDSA certs over RSA (smaller, faster signing)
    • OCSP Stapling (saves RTT)
    • HTTP/2 multiplexing (fewer TLS handshakes)
    • Connection pooling (reuse TLS sessions)
    • Async TLS offloading (non-blocking crypto operations)

─────────────────────────────────────────────────────────────────────────────
 API GATEWAY TLS
─────────────────────────────────────────────────────────────────────────────
  Client → [TLS] → API Gateway → [TLS or plain] → Services
                   (terminates TLS, rate limits, auth, routing)
  Advantages:
    • Central cert management
    • JWT/OAuth validation at gateway
    • Rate limiting and DDoS protection before reaching services

─────────────────────────────────────────────────────────────────────────────
 KUBERNETES INGRESS TLS
─────────────────────────────────────────────────────────────────────────────
  apiVersion: networking.k8s.io/v1
  kind: Ingress
  metadata:
    name: api-ingress
    annotations:
      cert-manager.io/cluster-issuer: letsencrypt-prod
  spec:
    tls:
    - hosts:
      - api.example.com
      secretName: api-tls-secret
    rules:
    - host: api.example.com
      http:
        paths:
        - path: /
          pathType: Prefix
          backend:
            service:
              name: api-service
              port:
                number: 8080

 22. REAL-WORLD SCENARIOS
================================================================================

─────────────────────────────────────────────────────────────────────────────
 SCENARIO 1: User opens https://bank.com on Chrome
─────────────────────────────────────────────────────────────────────────────
  1. DNS resolves bank.com → 93.184.216.34
  2. TCP 3-way handshake (SYN → SYN-ACK → ACK) on port 443
  3. ClientHello (TLS 1.3) with SNI="bank.com", ECDHE public key, cipher list
  4. Server selects cert for bank.com (SNI matched), picks TLS 1.3 + AES-256-GCM
  5. ServerHello + encrypted cert + CertificateVerify (signed with bank's private key)
  6. Chrome validates: chain → Let's Encrypt → ISRG Root X1 → trusted
  7. Chrome checks HSTS: bank.com is in preload list → confirms HTTPS
  8. Chrome checks CT logs: cert has 2 SCTs → trusted
  9. Chrome checks OCSP stapled response: "Good"
  10. Finished messages exchanged → session keys derived
  11. HTTP/2 GET / sent encrypted → HTML response encrypted
  Total: ~1 RTT for TLS + 1 RTT for HTTP/2 request

─────────────────────────────────────────────────────────────────────────────
 SCENARIO 2: Payment service calls Order service in Kubernetes with mTLS
─────────────────────────────────────────────────────────────────────────────
  1. Istio issues both services SPIFFE SVIDs via Envoy sidecar
     payment-svc cert SAN: spiffe://cluster.local/ns/default/sa/payment
     order-svc cert SAN: spiffe://cluster.local/ns/default/sa/order
  2. payment-svc app sends plain HTTP to localhost:8080 (local Envoy)
  3. payment Envoy intercepts → starts mTLS with order Envoy
  4. Both present SPIFFE certs → mutual authentication
  5. order Envoy decrypts → plain HTTP to order-svc app
  App code never knows about TLS — completely transparent.

─────────────────────────────────────────────────────────────────────────────
 SCENARIO 3: Certificate expires — what happens?
─────────────────────────────────────────────────────────────────────────────
  1. Server presents expired cert during handshake
  2. Client validates NotAfter < current time
  3. Client sends TLS alert: certificate_expired
  4. Handshake fails → connection refused
  5. Users see: "Your connection is not private (NET::ERR_CERT_DATE_INVALID)"
  Prevention:
    • Auto-renewal (cert-manager, Let's Encrypt, AWS ACM)
    • Monitoring alerts at 30, 14, 7 days before expiry
    • PagerDuty alert for < 7 days remaining


================================================================================
 23. TRICKY INTERVIEW Q&A (3 YOE LEVEL)
================================================================================

Q1: What is the difference between SSL and TLS?
A: SSL is the predecessor protocol developed by Netscape in the 1990s.
   TLS is the IETF-standardized successor. SSL 2.0 and 3.0 are both
   deprecated due to security vulnerabilities. Modern systems use
   TLS 1.2 or 1.3. The term "SSL certificate" is a misnomer — all
   certificates are X.509 certs used with TLS.

Q2: What is Perfect Forward Secrecy and why does it matter?
A: PFS ensures that even if a server's long-term private key is compromised
   in the future, past encrypted sessions cannot be decrypted. It's achieved
   through ephemeral key exchange (ECDHE/DHE), where a new key pair is
   generated for each session and discarded after. Without PFS (static RSA),
   recording today's traffic and later stealing the private key allows
   decryption of all recorded sessions. TLS 1.3 mandates PFS.

Q3: What happens during a TLS handshake?
A: TLS 1.3 handshake (1-RTT):
   1. Client sends ClientHello with supported ciphers, ECDHE public key, SNI
   2. Server responds with ServerHello (chosen cipher, its ECDHE key)
   3. Both derive shared secret via ECDHE
   4. Server sends encrypted Certificate + CertificateVerify + Finished
   5. Client verifies cert chain, sends Finished
   6. Encrypted data flows
   TLS 1.2 is similar but 2-RTT and cert is sent unencrypted.

Q4: How does certificate chain validation work?
A: Browser receives leaf cert + intermediate certs from server.
   It builds a chain from leaf → intermediate(s) → root.
   For each link: verify the issuer's digital signature on the subject cert.
   Root CA must be in the browser's/OS's pre-installed trust store.
   Also checks: validity period, hostname match (SAN/CN), key usage,
   revocation status (OCSP), and Certificate Transparency SCTs.

Q5: What is SNI and why is it needed?
A: Server Name Indication is a TLS extension where the client sends
   the target hostname in the ClientHello message. This allows a server
   with ONE IP address to host MULTIPLE domains, each with their own
   certificate. Without SNI, the server wouldn't know which cert to present
   before the handshake completes.

Q6: What is mTLS and when would you use it?
A: Mutual TLS requires BOTH client and server to present and validate
   certificates. Use cases: microservice-to-microservice auth (zero trust),
   IoT device auth, B2B APIs, regulated industries. Advantage over tokens:
   cryptographically unforgeable, automatically revocable, works at
   the network layer without application code changes.

Q7: What is HSTS and how does it prevent HTTPS downgrade attacks?
A: HTTP Strict Transport Security tells browsers to only use HTTPS for
   a domain for a specified period (max-age). Once seen, even if user
   types http://, browser internally upgrades to https:// without making
   an HTTP request. The HSTS preload list hardcodes domains in browsers
   so even first-ever visits use HTTPS. This prevents SSL stripping where
   an attacker downgrades HTTPS to HTTP.

Q8: What's the difference between TLS termination and TLS passthrough?
A: Termination: The load balancer/proxy decrypts TLS traffic and forwards
   unencrypted to backends. Simpler backend setup, but traffic is plain
   on internal network.
   Passthrough: LB routes encrypted packets to backend without decryption.
   Backend handles TLS. Full end-to-end encryption, enables mTLS to reach
   the backend. But LB can't do L7 routing or inspection.

Q9: Why did TLS 1.3 remove RSA key exchange?
A: RSA key exchange in TLS 1.2 worked by encrypting the pre_master_secret
   with the server's RSA public key. If someone records traffic today and
   later steals the private key, they can decrypt all those sessions. This
   violates Perfect Forward Secrecy. TLS 1.3 only allows ECDHE-based key
   exchange, where ephemeral keys are used and discarded, ensuring PFS.

Q10: What is OCSP Stapling and why is it better than basic OCSP?
A: Basic OCSP: client contacts CA's OCSP server during each handshake.
   Problem: privacy leak (CA knows which sites you visit), extra RTT,
   soft-fail means it's often bypassed.
   OCSP Stapling: SERVER periodically fetches its own OCSP response and
   includes ("staples") it in the TLS handshake. Client gets revocation
   status without contacting CA directly. Benefits: no privacy leak,
   no extra RTT, signed by CA so client can verify authenticity.

Q11: What are cipher suites and how do you evaluate them?
A: A cipher suite defines all the algorithms used in a TLS connection:
   key exchange (ECDHE), authentication (RSA/ECDSA), bulk encryption
   (AES-256-GCM), and message integrity (SHA-384).
   Good suites: use ECDHE (PFS), ECDSA or RSA-2048+ (auth), AES-GCM or
   ChaCha20 (AEAD encryption). Bad suites: static RSA key exchange,
   RC4, DES, 3DES, MD5, export-grade algorithms.

Q12: What is the 0-RTT feature in TLS 1.3 and what's the risk?
A: 0-RTT allows a client to send application data in the very first
   message (ClientHello), using a Pre-Shared Key from a previous session.
   This eliminates even the 1-RTT overhead on reconnection.
   Risk: 0-RTT data can be replayed by an attacker (no server Finished
   message before data is sent). Must only use for safe/idempotent
   requests (GET, not POST/PUT). Server should implement anti-replay
   mechanisms (nonce tracking, time windows).

Q13: How does Certificate Transparency (CT) work?
A: All publicly trusted CAs must log every cert they issue to
   append-only public CT logs (Merkle Tree-based). The log returns
   a Signed Certificate Timestamp (SCT). Browsers require 2+ SCTs
   in the TLS handshake. This means any cert issued for your domain
   by any CA is publicly visible — domain owners can monitor logs
   for unauthorized issuance. Tools: crt.sh, Google CT dashboard.

Q14: If I compromise a CA's private key, what can I do?
A: You can issue valid-looking certificates for ANY domain (including
   google.com, bank.com). Browsers would trust these certs since they
   chain to the compromised CA. This is why:
   - Root CAs keep private keys offline (air-gapped HSMs)
   - Certificate Transparency exists (unauthorized certs become visible)
   - Browser vendors can revoke CAs from their trust programs
   - Cert pinning protects specific apps
   DigiNotar 2011: CA was compromised, Google/Mozilla removed it from
   trust stores — killed the company.

Q15: What's the difference between a self-signed cert and a CA-signed cert?
A: A self-signed cert is signed with its own private key — no CA involved.
   No browser trusts it by default (you'd get a security warning).
   A CA-signed cert is signed by a trusted Certificate Authority.
   The CA has already verified your identity (domain, org, etc.) and
   is in browsers' trust stores, so browsers automatically trust it.
   Self-signed: OK for internal services/dev. CA-signed: required for public.

  SAN                   | Subject Alternative Name. Replaces CN for hostnames.

  mTLS                  | Both sides present certs. Used in microservices.
  HSTS                  | Browser always uses HTTPS. max-age + preload.
  SNI                   | Hostname in ClientHello. Enables virtual hosting.
  OCSP Stapling         | Server includes revocation status in handshake.
  TLS Termination       | LB decrypts TLS. Backends get plain HTTP.
  TLS Passthrough       | LB routes without decrypting.

  Session Ticket        | Stateless resumption. Server encrypts session state.
  0-RTT                 | TLS 1.3 feature. Replay risk. Use for GET only.
  SPIFFE                | Workload identity standard for microservices.
